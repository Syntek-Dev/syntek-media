# syntek-media

**A Copier template that adds audio and video production to a repository — brand, scripts, production and publishing layers, a small ffmpeg toolkit and a Claude Code skill suite — for a business or an author.**

![Version](https://img.shields.io/badge/version-0.5.0-blue)
[![Licence: MIT](https://img.shields.io/badge/licence-MIT-green.svg)](LICENSE)
![Template: Copier](https://img.shields.io/badge/template-copier-blue)

```bash
uvx --python '>=3.14' copier copy --trust gh:Syntek-Dev/syntek-media .
```

The quoted `--python '>=3.14'` makes `uvx` run Copier, and the family scripts that run inside it, on Python 3.14 or later; unquoted, the shell reads `>` as a redirection. Every Copier command in this README takes it.
Copier asks its questions, renders the layers for the brand kind, platforms and media kinds you choose, writes the files of the coding agents you tick, runs `git init` where no repository exists, makes the hooks in `.claude/hooks/` executable, sets a Git LFS tripwire where no LFS filter is configured, and warns where syntek-author's answers file stands without syntek-author's user guide. Last, on Python 3.14, its `baseline` task records the copy's render inside `.git` for later update reports and adds the settings entries and MCP servers media lists, once each, to a `.claude/settings.json` or MCP file the copy kept because it already existed.
Before copying into an existing project, check `.agents`. If it is a symbolic link (`test -L .agents`), such as `.agents -> .claude`, add `--exclude /.agents` to the copy command, then make the real folder as the bridge, `.claude/syntek-media-agents.md`, says. If `.agents/skills` is a real directory (`test -d .agents/skills && test ! -L .agents/skills`), preserve it and add `--exclude /.agents/skills`; integrate its skills manually afterwards. A `.agents/skills` link, whatever its target, needs no exclude: Copier skips it and leaves it as it is. Without the exclude Copier stops with an `AssertionError` before its skip check, because a path that resolves to a directory meets a link in the template. Fresh projects receive a real `.agents/` folder holding `skills -> ../.claude/skills` and `mcp_config.json`; Copier's update never writes under `.agents` (D76), and since 0.6.0 the update script only adds the two MCP servers, once, to an `.agents/mcp_config.json` that exists where Antigravity is recorded, never through a link (D81).
If `.agents` is a link to a folder outside the project, Copier refuses to render anything beneath it, `--exclude` included, so move the link aside for the copy and put it back: `mv .agents .agents.syntek-held`, copy with `--exclude /.agents`, then `mv .agents.syntek-held .agents`. The link's target is never touched; updates on Python 3.14 do the same for you (see Migrations, below).
It is built to be applied inside a project generated by syntek-author, beside its writing layers, and it also renders on its own into an empty folder.
New here? Start with [the user guide](template/how-to/src/TEMPLATE-GUIDE/syntek-media/01-overview.md), the same chapters every project carries in `how-to/`.

## What it generates

One template, three brand kinds. You choose the kind once, with `BRAND_KIND`, and it cannot be changed later.

| Brand kind          | For                                                                 | Applied over syntek-author's | What is particular to it                                                                                                                                                                        |
| ------------------- | ------------------------------------------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `business`          | A business's social video, recorded talks and explainers            | `business`                   | Business mode files; where syntek-author's social-media family is present, it owns the written social plan, the content calendar and the bios, and media's profiles, schedule and posts cite it |
| `author-fiction`    | A novelist's book trailers, audiobook and author socials            | `fiction`                    | Fiction mode files: trailers built from stills, cards, fades and push-ins; the spoken form of constructed names; audiobook narration from the promoted manuscript                               |
| `author-nonfiction` | A non-fiction author's talks, podcast, audiobook and author socials | `theology`                   | Non-fiction mode files: recorded talks cut into clips and podcast episodes; quotation and scripture-translation permissions for audio as worked examples; the audiobook                         |

Every brand kind shares the same spine:

- **The piece and its ladder.** One deliverable work — a short, an explainer, a talk, a trailer, a podcast episode, an audiobook, a standalone voiceover — lives in `scripts/src/pieces/NNN-kebab-title/` and moves from `idea` to `published` through seven gates, M1 to M7, defined in `scripts/docs/reference/the-piece-ladder.md`. A recorded talk enters with an approved transcript instead of a script, and an audiobook with an approved chapter register.
- **Production layers.** `brand/` (the visual tokens and layouts, the spoken voice, one profile per platform), `scripts/` (briefs, scripts, transcripts, storyboards and shot lists), `production/` (the footage manifest, voiceover, word and mouth timings, scene files, edit decision lists, cards, masters, rights and credits) and `publishing/` (cut-down plans, captions, thumbnails, post packages, the schedule and the publish log), each with reference guides in `docs/reference/`, numbered workflows and a place for your own procedures. **A supporting layer**, `toolkit/`, holds the production code.
- **The production code.** One standard-library command line, `python3 toolkit/media.py`, drives ffmpeg for masters, cuts, encodes, loudness, captions and burn-in, images (JPEG, WebP, AVIF, posters) and GIF previews, and writes a self-hosted podcast's RSS feed with the standard library; `uv run toolkit/card.py` renders the brand's HTML and CSS layouts to PNG thumbnails and cards with a pinned Playwright. Platform limits are dated data in `toolkit/data/platforms.toml`, never numbers in a guide. Every output a piece makes lands in a folder named for it, and `python3 toolkit/media.py where <piece>` lists the piece's tracked files and names those folders.
- **Audio.** ElevenLabs voiceover, narration and speech-to-text through your user-scope MCP server: never unasked, the cost stated first, one call at a time, every spend logged.
- **Design.** The brand's tokens and its thumbnail and card layouts live in `brand/src/design-system/`, kept in step with its Claude Design project by `/design-sync`, which you start, one component at a time.
- **Claude Code configuration.** Skills only, no agents; the rules in `.claude/rules/syntek-media/`; hand off, never compact.
- **The user guide.** `how-to/`, read-only, in every project: media's chapters, guides and step-by-step procedures, beside three chapters shared with syntek-author (see [The user guide](#the-user-guide)).

Platforms and media kinds add to a brand kind. Each is a multiple choice, and every brand kind is offered every value:

| Platform     | On by default for                     | Adds                                                                                                                                                                                                                                                  |
| ------------ | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `youtube`    | every brand kind                      | `brand/src/platforms/youtube.md` (your profile, a seed) and `publishing/docs/reference/youtube.md` (limits by data key, the disclosure setting, captions, thumbnails, the platform's traps)                                                           |
| `tiktok`     | `author-fiction`                      | the same two files for TikTok                                                                                                                                                                                                                         |
| `instagram`  | every brand kind                      | the same two files for Instagram                                                                                                                                                                                                                      |
| `linkedin`   | `business`                            | the same two files for LinkedIn                                                                                                                                                                                                                       |
| `facebook`   | `author-fiction`, `author-nonfiction` | the same two files for Facebook                                                                                                                                                                                                                       |
| `podcast`    | `author-nonfiction`                   | the same two files for Apple Podcasts and Spotify, and, for a show you serve yourself, `publishing/docs/reference/podcast-feed.md`, `publishing/workflows/08-publish-the-podcast-feed/` and `publishing/src/podcast/` (your show registers and feeds) |
| `website`    | none                                  | `brand/src/platforms/website.md` (your sites, each with its agreement where you do not own it) and `publishing/docs/reference/website.md` (self-hosted or embedded video, posters, share images, captions and transcripts, the hosting tests)         |
| `blog`       | none                                  | the same two files for blog posts: the video, its transcript, featured and share images                                                                                                                                                               |
| `newsletter` | none                                  | the same two files for email issues: a linked preview image or GIF, never video (your lists, never a subscriber)                                                                                                                                      |

**One `website` platform covers every site** you publish media to, your own and any you write for: each site is a row of your website profile, named by a slug, and one render serves every page that uses its key. Media makes the files and the few words outside the page (alt text, an embed's title, the structured-data values); the page, post or issue itself, its words and its date are the written side's, syntek-author's where it is present. Media never edits a website, sends an email or holds a subscriber list.

**Self-hosting a podcast.** A podcast can go to Apple Podcasts, Spotify and YouTube and be served from your own website or websites. A show you serve yourself has one RSS feed, written by `python3 toolkit/media.py feed` from its show register and uploaded by you, with the episode audio, art, captions and chapters, to one site you own; Apple Podcasts and Spotify read that feed, and YouTube takes each episode as video, uploaded into the show's podcast playlist. An episode reaches the feed by one of two routes: a talk published whole as an episode (one piece, its `youtube.long` and its `podcast.feed_audio` from one master; `MEDIA_KINDS` needs only the talk's own kind) or an episode of its own (a `podcast` piece, mastered by the podcast-episode workflow; `MEDIA_KINDS` needs `podcast`). A page on another site that plays the episode is a placement with its own agreement, never a second feed. A show kept on a podcast host instead delivers `podcast.apple_rss_audio` to the host and uses neither the register nor the feed workflow. Choose `podcast` for either, and `website` beside it for episode pages on your own site.

| ------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `short-video` | every brand kind                      | `scripts/docs/reference/short-video.md`                                                                                                                                                                            |
| `long-video`  | `business`, `author-nonfiction`       | `scripts/docs/reference/long-video.md`                                                                                                                                                                             |
| `podcast`     | `author-nonfiction`                   | `scripts/docs/reference/podcast-episodes.md` and `production/workflows/04-master-a-podcast-episode/`                                                                                                               |
| `audiobook`   | `author-fiction`, `author-nonfiction` | the `narrate-audiobook` skill, `production/src/audiobook/`, `production/workflows/05-narrate-an-audiobook/`, `production/workflows/06-master-an-audiobook/` and `production/docs/reference/audiobook-narration.md` |
| `trailer`     | `author-fiction`                      | `scripts/docs/reference/trailers.md`                                                                                                                                                                               |
| `voiceover`   | every brand kind                      | `scripts/docs/reference/standalone-voiceovers.md`, the guide to a piece that is only a voiceover. The `voiceover` skill, its workflow and its folder ship whatever you choose                                      |

`SEED_EXAMPLES` adds one worked example piece, once.

The writing skills — spelling, grammar, comprehension, flow, fact-check, improve-section, adapt-section and research — come from syntek-author and are never shipped here.
Media's files name each one as a companion, 'the spelling skill (syntek-author), where present', and its skills check that the companion exists before they use it.
The seven working-practice skills — `grilling`, `grill-me`, `grill-with-docs`, `wayfinder`, `handoff`, `to-questionnaire` and `wait-what` — ship with both templates, byte for byte the same (D80).

## Requirements

Scene rendering uses the same pinned Playwright/Chromium as cards; systemd memory caps are optional.

| Tool                                                   | Needed for                                                                                                                                                                                                                                                             |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [uv](https://docs.astral.sh/uv/) (`uvx`)               | Running Copier without installing it, Copier 9.12.0 or newer on Python 3.14 or newer, and `uv run toolkit/card.py`; the two MCP servers also start through `uvx`. Left to itself, `uvx` may run Copier on an older Python it already has, and then the copy's `baseline` task and every update's script do nothing but warn that they did not run, so every Copier command here asks for `--python '>=3.14'` (quoted, or the shell reads `>` as a redirection); uv fetches that Python the first time if it has none. |
| git 2.31 or later                                      | Every project is a repository; updates are three-way merges, and the update script reads the Git history of the files it updates.                                                                                                                                                                                                         |
| Python 3.14 or newer                                   | One minimum for everything the project runs but word alignment (below): the standard-library `media.py` toolkit, the session hooks, the data-root and permissions scripts in `.claude/` (`syntek-media-dataroot.py`, `syntek-media-permissions.py`), and the update script that ends every update and copy, which runs on the Python that runs Copier (the uv row). Author data is TOML and generated timing is JSON. On an older Python the toolkit and the two `.claude/` scripts refuse, a hook lets the action through and warns, and the update and outside-link scripts change nothing but say so in a message framed in lines of `=`. Optional dependency workers are described below. |
| ffmpeg and ffprobe                                     | Masters, cuts, encodes, loudness and burned-in captions. Built with libass, x264 and mp3lame. With libwebp, an AV1 encoder (libaom-av1 or libsvtav1) and the `avif` muxer (optional), `media.py image` also writes WebP and AVIF images; `check --setup` reports them. |
| Playwright's Chromium                                  | Thumbnails and cards rendered to PNG. Install it once with `uv run --with playwright==1.64.0 playwright install chromium`, or use a system bundle at the same revision (NixOS); nothing is installed globally.                                                                                                              |
| git-lfs                                                | Large design exports in `brand/src/exports/large/`, and nothing else.                                                                                                                                                                                                  |
| espeak-ng (optional)                                   | An offline scratch voice for timing a script, labelled approximate.                                                                                                                                                                                                    |
| An ElevenLabs MCP server named `elevenlabs` (optional) | Voiceover, narration and speech-to-text, added at user scope (see [Audio with ElevenLabs](#audio-with-elevenlabs)).                                                                                                                                                    |
| syntek-author v0.6.0 or later (recommended)            | The writing skills and the project settings file. Media works without them, with less; the handoff skill and the other working-practice skills ship with both templates. In a combined project, update syntek-author to v0.6.0 or later before applying or updating media: an older one has no user guide beside media's, and the copy warns where its guide is missing. |
| Codex, Gemini CLI, Antigravity or OpenCode (optional)  | Other coding agents, each reading the same rules, skills and memory through the bridge, `.claude/syntek-media-agents.md`. A copy writes the files only of the clients ticked in `AGENT_CLIENTS` (see [Using other coding agents](#using-other-coding-agents)). |
| The `scrapling` and `code-review-graph` MCP servers (optional) | Web pages, and a local map of the code. Both are pinned and keyless in `.mcp.json` and each client's own file, and start through `uvx`; the first start downloads them, and Scrapling drives Playwright's Chromium. |
| [Claude Code](https://code.claude.com/)                | The skills, rules and workflows.                                                                                                                                                                                                                                       |

In a generated project, `python3 toolkit/media.py check --setup` reports the toolkit's own tools in this table (uv, Python, ffmpeg and ffprobe, Playwright's Chromium, git-lfs, espeak-ng and the ElevenLabs server), and the ElevenLabs permissions and base path, without changing anything. It never looks for syntek-author, the other coding agents or the `scrapling` and `code-review-graph` servers, and of the settings entries it reports media's own only.

Optional word alignment uses `toolkit/transcribe.py` (WhisperX 3.8.6, which needs a Python from 3.10 to 3.13), the one tool outside the 3.14 minimum, launched through `media.py transcribe`. Set `MEDIA_TRANSCRIBE_PYTHON`, at user scope, to the path of that older interpreter, kept beside 3.14 and never activated where Claude Code or `media.py` runs, whose `python3` the hooks and the family scripts need at 3.14. Without it `media.py` asks uv, offline, for a Python in that range, and never uses a `UV_PYTHON` outside it; where none qualifies it exits 2, naming `MEDIA_TRANSCRIBE_PYTHON`. The author runs `python3 toolkit/media.py transcribe fetch` once for English wav2vec2 weights, nltk's punkt_tab and the cross-check model; skills and audits never fetch them or build the WhisperX environment. Author-edited data is TOML; tool-written timing is finite JSON. Captions can follow accepted word timings with `captions from-words`, preserving the first and last word of each cue.

## Applying to a syntek-author project

syntek-media is built to be applied inside a project generated by syntek-author — a business document library, a novel or a theology book — with its own answers file beside syntek-author's.
Apply syntek-author first, then media: a `business` project takes `business`, a `fiction` project `author-fiction`, a `theology` project `author-nonfiction`.
Nothing moves: every folder media adds is new, and every root file the two templates share is already there and is left exactly as it is.
The project's syntek-author must be v0.6.0 or later, updated to it before media is applied or updated (D84): an older one calls every `src/` folder the author's, lints `how-to/src/` by default and puts nothing in `how-to/` back. Where `.copier-answers.syntek-author.yml` stands without syntek-author's guide, a copy-only task warns, without failing, that syntek-author must be updated first.

1. **Start from a clean, committed tree, on a branch.**

   ```bash
   git switch -c apply-syntek-media
   ```

2. **Copy the template into the project**, answering the questions, or with an answers file you have edited from one of the example answers files in `examples/` on GitHub, one per brand kind, taken at the release tag you copy so that it names only that release's questions:

   ```bash
   uvx --python '>=3.14' copier copy --trust gh:Syntek-Dev/syntek-media .
   ```

   ```bash
   TAG=$(git ls-remote --tags --refs --sort=-v:refname https://github.com/Syntek-Dev/syntek-media.git 'v*' | sed -n '1s#.*refs/tags/##p')
   curl -fsSL -o /tmp/answers.yml \
     "https://raw.githubusercontent.com/Syntek-Dev/syntek-media/$TAG/examples/business.answers.yml"   # then edit every value
   uvx --python '>=3.14' copier copy --trust --vcs-ref="$TAG" --data-file /tmp/answers.yml \
     --data SEED_EXAMPLES=false gh:Syntek-Dev/syntek-media .
   ```

   `TAG` is the latest release on GitHub, the one a plain `copier copy` renders; `--vcs-ref="$TAG"` holds the copy to the same release as the answers file. In your copy of the example, delete the `DATA_*` lines, and the coding-agent lines (`AGENT_CLIENTS`, `CODEX_MODEL`, `GEMINI_MODEL` and the four `OPENCODE_*` keys), wherever syntek-author records its own: media then takes syntek-author's answers. Every syntek-author project from its v0.5.0 records the data-root answers, and a first answer that differs is refused, because one project keeps one store.
   The coding-agent answers follow the same records since 0.6.0 (D81): a first copy records syntek-author's clients and models where its answers file records them, and all four clients otherwise, and takes the OpenCode address, model and context only from a record with the same `OPENCODE_PROVIDER`. So it writes no client file syntek-author's answers left out, and the model tables in both templates' rules agree.
   **Never pass `--overwrite`.** Copier leaves existing shared files alone, printing each as `conflict` then `skip` (or as `identical`, where the two copies match). That pair is expected and is not a collision; missing shared paths are filled by media.
   Any other path that already exists is a collision, which is a template bug: a non-interactive copy stops with 'Interactive session required' before it writes that file, and an interactive one asks 'Overwrite …?' with yes as the default — answer no.
   Either way, `git status` shows anything written before the stop; remove it and report the collision.

3. **Review `git diff`, then make the hand edits** below, which the shared files cannot learn from a copy that skipped them.

4. **Commit**, including `.copier-answers.syntek-media.yml`. From here, each template updates separately (see [Updating a project](#updating-a-project)).

There are no adoption scripts.
Every media folder is new, so no move has exactly one right destination, and loose media already in the repository — old footage, a folder of social clips — is yours to sort.

### The hand edits after a copy

The copy prints these at the end, with your answers filled in:

1. **`.claude/settings.json`** — syntek-author's settings allow neither the toolkit nor ffmpeg, so every toolkit call would prompt. Add the four `Bash(…)` entries to `permissions.allow` by hand, beside the entries already there: no copy or update of either template offers an allow (`WebSearch` and `WebFetch`, the seed's other two, are already allowed by syntek-author's settings):

   ```json
   "allow": [
     "Bash(python3 toolkit/*.py *)",
     "Bash(uv run toolkit/*.py *)",
     "Bash(ffmpeg *)",
     "Bash(ffprobe *)"
   ]
   ```

   Everything else media's refresh data, `migrations/family-refresh.json`, lists for this file, the copy's last task, `baseline`, has already added to the file the copy kept, once each and on Python 3.14, never removing or changing an entry of yours, and never adding one any earlier commit of the file held, which it names instead (D81): `"autoCompactEnabled": false` and `"idleCompaction": false` where each key is absent; the nine ElevenLabs asks and the two `voice remix run` asks; syntek-author's eight Scrapling and code-review-graph asks; the denies `AskUserQuestion`, `Edit(**/generated/**)`, `Edit(**/renders/**)`, `Edit(/how-to/**)` and `mcp__code-review-graph__embed_graph_tool`; the four handoff-hook entries (`UserPromptSubmit`, `PreCompact` `auto` and `manual`, and `SessionStart` `compact`); and the guide guard's `PreToolUse` entry. One you already allow is reported, not added.
   The ElevenLabs server marks every tool as read-only, so only an `ask` rule makes Claude Code stop before a call that spends credits. Voice remix is the one ElevenLabs call the toolkit makes itself, because the server has no remix tool; the toolkit `allow` entries would let `python3 toolkit/media.py voice remix run` spend credits unprompted, so its two `ask` entries, which take precedence over an `allow`, make Claude Code stop first. ## Generating a standalone project

From the published template on GitHub, at its latest release tag:

```bash
uvx --python '>=3.14' copier copy --trust gh:Syntek-Dev/syntek-media my-channel
```

Copier records `gh:Syntek-Dev/syntek-media` in the answers file, and every later update reads the template from there.

**The `MissingFileWarning` is expected.** On a fresh copy, and on every update, Copier may warn that `.copier-answers.syntek-media.yml` was not found. It is harmless. The template looks for your previous answers so that an update can refuse a changed `BRAND_KIND`; on a first copy there are none yet, and an update's temporary renders read the path too. Since 0.5.0, where syntek-author has never been applied, Copier also warns that `.copier-answers.syntek-author.yml` was not found, on every copy and update. That is harmless too: Copier reads syntek-author's answers file only for the family questions' defaults and validators (its data-root answers and, since 0.6.0, its client and model answers) and, after an update, to report a data-root difference, so that one project keeps one store and one set of agent clients (DESIGN.md D14, D80, D81).

**Why `--trust`.** After rendering, the template runs five small tasks, all on a copy only: `git init` (only where no repository exists); `chmod +x` on the hooks in `.claude/hooks/`, because a checkout of the template does not always carry the bit; the Git LFS tripwire, which sets `filter.lfs.required` in the repository's own `.git/config` where no LFS filter is configured, so that a large design export cannot be committed whole by mistake; a warning where `.copier-answers.syntek-author.yml` stands without syntek-author's user guide (D84); and, last, syntek-author's `baseline` task (`migrations/family-update.py baseline`), which on Python 3.14 records the copy's render under `refs/syntek-media/` inside `.git`, so that the first update reports from it, refreshes a listed shared file that equals an earlier recorded render, and offers the listed settings entries and MCP servers, once each, to the files the copy kept (D81). On an older Python it records nothing and prints, framed in lines of `=`, that family-update did NOT run. Copier treats any task as an unsafe feature and refuses to run one without `--trust`. Every task is non-fatal.

Without prompts, for scripts and CI, pass every answer that has no default and accept the rest:

```bash
uvx --python '>=3.14' copier copy --trust --defaults \
  --data BRAND_KIND=author-fiction \
  --data "BRAND_NAME=Morgan Example" \
  --data "BRAND_DESCRIPTION=Trailers, read-aloud clips and the audiobook of a fantasy novel, for readers who have not yet opened the book." \
  --data 'PLATFORMS=[youtube, tiktok, instagram]' \
  --data 'MEDIA_KINDS=[trailer, short-video, audiobook]' \
  --data DATE=03/10/2026 \
  gh:Syntek-Dev/syntek-media morgan-example-media
```

`BRAND_KIND` has no default on purpose: without it, `--defaults` stops with an error rather than quietly generating a business brand.
A list takes the choice values, never their labels.

Standalone, the shared files are media's own copies, and the project works without the writing companions: there is no writing router and no project settings file, and a skill that would use a companion says which one is missing. The working-practice skills (`grilling`, `grill-me`, `grill-with-docs`, `handoff`, `to-questionnaire`, `wait-what` and `wayfinder`), the two handoff hooks in `.claude/hooks/`, the `handoffs/` folder, the user guide's shared files and its guard, `.claude/hooks/how-to-read-only.sh`, ship with media as they do with syntek-author, byte for byte the same (D80, D84), and later updates refresh each of these family-shared files you never changed (D81).
When generation finishes, open the project in Claude Code. The generated `README.md` and `CONTEXT.md` describe that project; `.claude/CLAUDE.md` holds its brief and points at the rules.

## What `copier update` will and will not touch

Every file in a generated project belongs to one of five classes. Knowing which is which is the whole of updating safely.

**1. Template files — updated, and merged with your edits.**
The rules in `.claude/rules/syntek-media/`, media's own skills and the `MEDIA-<KIND>.md` mode files it adds to five of the working-practice skills, the bridge, data-root and permissions files in `.claude/` (`syntek-media-agents.md`, `syntek-media-dataroot.py`, `syntek-media-dataroot.json` and `syntek-media-permissions.py`), every folder's `CONTEXT.md` and `CLAUDE.md` (apart from the seeded and shared ones below), the reference guides in `docs/reference/`, the numbered workflows, the toolkit with its platform data and fallback layouts, every nested `.gitignore` and `.gitattributes`, and the `README.md` of every `generated/`, `renders/` and `raw/` folder.
An update brings the template's improvements and keeps your local edits through a three-way merge; where both changed the same lines you get a conflict to resolve.
Better than editing them: put your own guide in `docs/project/` (a guide there with the same name overrides the reference guide, though it may only add checks to a gate of the piece ladder, never remove one), your own procedure in `workflows/local/` (a local workflow with the same name overrides the template's), a confirmed change to a platform's limits as an `[[override]]` row in `brand/src/platforms/overrides.toml`, and your own rules where syntek-author's project settings file says, or in `.claude/CLAUDE.md` under 'Project-specific rules' in a standalone project.
**Media's own user-guide files are read-only**: everything under `how-to/docs/syntek-media/`, `how-to/src/TEMPLATE-GUIDE/syntek-media/` and `how-to/workflows/syntek-media/`. Every full update puts back the template's version of each one that differs, conflict markers and a deletion included, and Git keeps your edit (`HEAD`, and `refs/syntek-media/yours` inside `.git`); record a departure from the guide as [The user guide](#the-user-guide) says, never in `how-to/`.

**2. Seeds — written once if missing, then yours.**
The design register, `tokens.css` and the seven preview cards in `brand/src/design-system/` (among them `thumbnail.html` and `card.html`, the brand's own layouts), `voice.md`, `overrides.toml` and one profile per platform in `brand/src/platforms/`, the piece register, the rights register, the credits log, the footage manifest, the schedule, the publish log, and the `CONTEXT.md` and `CLAUDE.md` of every `docs/project/` and `workflows/local/` (you add a row to them).
An update never overwrites one that exists. If you delete one, the next update puts a fresh, empty copy back, because skills and rules read it by path.
The cost: once a seed exists it never receives the template's improvements. A release that must change a seed ships a migration that edits your copy only where exactly one change is correct.
**The one exception: removing a platform or a media kind deletes every file it generated, seeds included**, even a platform profile you have filled in (see [Updating a project](#updating-a-project)).

**3. Copy-only shared files — written once by a copy; Copier's update never renders them.**
Fifty paths (D11, D80, D84): `README.md`, `CONTEXT.md`, `.gitignore`, `.mcp.json`, `.claude/CLAUDE.md`, `.claude/CONTEXT.md`, `.claude/MEMORY.md`, `.claude/settings.json` and the `CONTEXT.md` and `CLAUDE.md` of `.claude/skills/`, plus `AGENTS.md`, `GEMINI.md`, `.agents`, `.codex/config.toml`, `.codex/CONTEXT.md`, `.codex/CLAUDE.md`, `.claude/mcp_config.json`, `.agents/skills` and `.agents/mcp_config.json` (D73, D76).
Since 0.4.2 `.agents` is the real folder that holds the last two, and `.claude/mcp_config.json` is no longer written by a copy: Antigravity reads `.agents/mcp_config.json`. A project that already has it keeps it.
Since 0.5.0 (D80) also `.gemini/settings.json`, `.gemini/CONTEXT.md`, `.gemini/CLAUDE.md` and `opencode.json`; the `SKILL.md` of the seven working-practice skills (`grill-me`, `grill-with-docs`, `grilling`, `handoff`, `to-questionnaire`, `wait-what` and `wayfinder`); `.claude/hooks/pre-compact-handoff.sh`, `.claude/hooks/context-threshold-handoff.sh` and the `CONTEXT.md` and `CLAUDE.md` of `.claude/hooks/`; and those of `handoffs/`.
Since 0.6.0 (D84) also the user guide's shared files: the `CONTEXT.md` and `CLAUDE.md` of `how-to/`, `how-to/docs/`, `how-to/src/`, `how-to/src/TEMPLATE-GUIDE/` and `how-to/workflows/`, the three shared chapters `how-to/src/TEMPLATE-GUIDE/agent-clients-and-mcp.md`, `how-to/src/TEMPLATE-GUIDE/the-data-root.md` and `how-to/src/TEMPLATE-GUIDE/updating-and-recovery.md`, and the guide guard, `.claude/hooks/how-to-read-only.sh`.
'Copy-only' is this class. 'Family-shared' names the thirty-nine of them that are syntek-author's files, byte for byte the same in both templates: the client files, `.mcp.json`, the working-practice skills, the hooks with their pair, the `handoffs/` pair and the guide's shared files. A coding agent's files are written only for the clients ticked in `AGENT_CLIENTS`.
A copy writes one only where it does not already exist; existing shared paths remain the author's, and media fills only missing paths. In a standalone project they are media's initial copies, and yours to edit.
Copier's update never renders one, so your edits are never merged into it. Since 0.6.0 the update script that ends every update, on Python 3.14, acts on thirty-three of them, as media's `migrations/family-refresh.json` lists (D81):

- **(a) It refreshes the twenty-seven listed family-shared files** — the seven `SKILL.md`, the three hooks with the `.claude/hooks/` pair, the `handoffs/` pair and the thirteen shared files of the guide. It replaces one only where it still equals a render the project held and the new release changed it, and writes one only where you never had it. An edited one, or one holding syntek-author's version, is kept and reported, never downgraded; one you deleted stays deleted, outside `how-to/`, which every full update puts back.
- **(b) It offers the listed entries and servers, once each.** The copy's `baseline` task and every update add to `.claude/settings.json` the listed settings entries and top-level values it lacks, and the two MCP servers, `code-review-graph` and `scrapling`, to `.mcp.json` and to the MCP files of the clients the answers record (`.agents/mcp_config.json`, `.codex/config.toml`, `.gemini/settings.json` and `opencode.json`; `opencode.json` and `.gemini/settings.json` only once `--write` has given them every ask form), never to `.claude/mcp_config.json`. It never removes, reorders or weakens an entry, and never adds back one it counts as offered, so one you removed after it was committed stays removed. It never creates an MCP file.
- **(c) It never writes the other seventeen after the copy**: `README.md`, `CONTEXT.md`, `.gitignore`, `.claude/CLAUDE.md`, `.claude/CONTEXT.md`, `.claude/MEMORY.md`, the `.claude/skills/` pair, `AGENTS.md`, `GEMINI.md`, `.agents`, `.agents/skills`, the `.codex/` and `.gemini/` pairs and `.claude/mcp_config.json`. One of these you delete stays deleted, and the client entrypoints never arrive by update.

Neither (a) nor (b) happens below Python 3.14, under `SYNTEK_UPDATE_REPORT=off`, on a `--pretend` run or after a failed render; the next full update delivers it.

**4. Examples — copied once, and they stay deleted.**
The worked example piece `000-example-piece`, with its edit decision list, title card, cut-down plan, captions, thumbnail and post package. They arrive on the first `copier copy` (unless `SEED_EXAMPLES` is false) and an update never renders them again: delete them when you are done and they never come back; keep and edit them and an update leaves them alone.
The example is a plan, walked through to `storyboarded`: it names footage no project has, so `media.py assemble` on it stops for want of that footage, as it should.

**5. Your folders — the template ships only the signposts.**
`scripts/src/pieces/` (each piece folder then carries its own pair), `production/src/footage/`, `assets/`, `edits/`, `cards/`, `voiceover/`, `timing/`, `scenes/` and `audiobook/`, `publishing/src/cut-downs/`, `captions/`, `thumbnails/` and `posts/`, `brand/src/design-system/fonts/`, `brand/src/exports/` and `exports/large/`, `brand/src/voice/` and `brand/src/platforms/`, and every `docs/project/` and `workflows/local/`.
The template ships each folder's `CONTEXT.md` and `CLAUDE.md` (and any seed or ignore file named above) and nothing else, so nothing you put there is ever touched.
`how-to/` is not one of your folders: it is the template's user guide, read-only. A file of yours there that no template ships is never touched, and the update that crosses 0.6.0 lists it.

Your scripts, transcripts, footage, takes, renders and published copy are never template files.

## Updating a project

Always on a branch, always with the answers file named, with Copier on Python 3.14 and with Git's automatic housekeeping off for the run. In a combined project, update syntek-author first, to v0.6.0 or later, and commit, then update media:

```bash
git switch -c update-syntek-media
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx --python '>=3.14' copier update --trust -a .copier-answers.syntek-media.yml
git status && git diff     # review; resolve any conflict markers
git add -A && git commit -m 'Update from syntek-media'
```

**Why housekeeping off.** Copier renders the template into temporary Git repositories and commits in them, and after a commit Git may start its automatic maintenance in the background. If that is still writing when Copier deletes the temporary folder, the update stops with `OSError: [Errno 39] Directory not empty` on a `.git/objects` path under a `copier._main.old_copy.…` or `copier._main.new_copy.…` folder. It is intermittent, most likely with Git 2.54 or 2.55 (Git 2.56 starts the background repack only above about 7,000 loose objects) and with several updates running at once. The five variables in front of the command turn `gc.auto` and `maintenance.auto` off for that one command, in every Git it starts, and change none of your Git settings. The form is for POSIX shells such as bash and zsh, and needs Git 2.31 or later. Give every other update command in this README the same five variables in front.

**If an update stopped with that error,** Copier had already written the new version's files and recorded the new version in `.copier-answers.syntek-media.yml`, but nothing that runs after the render had run: no after-stage migration (the release's own report, such as 0.4.2's or 0.6.0's, included), no update report, no refresh of the shared files, no settings entry or MCP server added, no restore of the user guide, no message after the update, and an `.agents` link outside the project is still held aside. Never commit that state: an update run over it takes the new version as already reached, so it reports 'Keeping template version 0.6.0' and skips that release's migrations. Discard it and run the update again, from the project root, in this order. First, if `.agents.syntek-held` exists, put the link back as 'Migrations' below says: `git clean -fd` would delete it. Next run `git clean -n -d`, a dry run that deletes nothing: it lists every untracked file and folder the discard would delete, not only the update's (Copier refuses to start over untracked files only where Git shows them: with `status.showUntrackedFiles` set to `no`, it runs over yours), so commit or move out of the project anything of yours it lists; files Git ignores are left alone. `git reset --hard` discards every uncommitted change in the repository, so the project must be its own repository. Then:

```bash
git reset --hard && git clean -fd
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx --python '>=3.14' copier update --trust -a .copier-answers.syntek-media.yml
```

Where it stopped with `FileExistsError` or `NotADirectoryError` naming `how-to`, `how-to` is a file; where it stopped with `ForbiddenPathError` naming a path in `how-to`, `how-to` is a link that leads outside the project. Either way, after the discard and before the second run, give it another name and commit (`git mv how-to my-how-to` for one Git tracks), as [updating and recovery](template/how-to/src/TEMPLATE-GUIDE/updating-and-recovery.md#when-an-update-stops) says, or the second run stops the same way.

The second run updates from the version you had (Copier prints 'Updating to template version 0.6.0', say, not 'Keeping template version 0.6.0', and the report reads '0.5.0 → 0.6.0'), runs every migration the crossing calls for, and delivers what an update that never stopped delivers.

**The update report and the records.** Discarding an update and running it again is safe; run template updates on one line of history, because the update's record is kept per clone, not per branch. Every update on Python 3.14 ends with media's report, opening '▸ syntek-media update report' and the two versions, of each file the new version changed that it did not deliver, each with a command to compare it and one to take the template's version; and it puts back the user guide's files in `how-to/`, which is read-only, listing each. `git log -1 --format=%B syntek-media/template` prints the last report again. The report's records live in `.git` under `refs/syntek-media/`: `git push --mirror` publishes them, and `syntek-media/yours` keeps your `HEAD` at the update reachable, so delete both with `git update-ref -d` before rewriting history to remove a secret. To mirror a repository without them, configure the remote instead of using `--mirror`: `git config remote.<name>.push '+refs/*:refs/*'`, `git config --add remote.<name>.push '^refs/syntek-media/*'`, then `git push --prune <name>`. A skill of the same name in your own `~/.claude/skills/` replaces the project's shared one, which no update then reaches. Scripts add `--defaults`. Every step, the report's sections and recovery are in [updating and recovery](template/how-to/src/TEMPLATE-GUIDE/updating-and-recovery.md) and media's procedures [`how-to/workflows/syntek-media/04-update-the-template/`](template/how-to/workflows/syntek-media/04-update-the-template/) and [`how-to/workflows/syntek-media/05-recover-a-stopped-update/`](template/how-to/workflows/syntek-media/05-recover-a-stopped-update/).

**Where no report appears.** If no '▸ syntek-media update report' line appears, Copier ran no migration (it could not read a template version): run `git status`, and look for `.rej` files and conflict markers. If a message framed in lines of `=` says family-update did NOT run, Copier ran on a Python older than 3.14, and nothing was reported, refreshed, added or put back: upgrade to Python 3.14, look for `.rej` files and conflict markers, commit, then run the same update again as above. An update under `SYNTEK_UPDATE_REPORT=off` prints only conflicts and deletions, a `--pretend` run runs no migration, and where the script's own render fails it reports only conflicts and deletions; each skips the refresh, the offers and the restore, which the next full update delivers.

**Updating to 0.6.0.** The update that crosses 0.6.0 prints media's crossing report once: where the user guide starts, that it is read-only, and, where the project holds syntek-author, syntek-author's guide beside it or that syntek-author must first be v0.6.0 or later. Update syntek-author to v0.6.0 or later first. Commit or move any untracked file under `how-to/` first, because Copier may write over it before any script runs where `status.showUntrackedFiles` is `no`, and `how-to` must be a real folder: a file there stops the update, a link outside the project stops it, and a link inside the project makes Copier write through it. Then the update script writes the shared files of the guide and its guard, the working-practice skills, hooks and pairs a project made before 0.5.0 lacks, and the listed settings entries and servers your files lack, once each; it creates no client file, and changes an existing one only by adding the two servers once.

**Why Python 3.14.** Every update ends with media's update script, `migrations/family-update.py`, and the outside-link pair runs around the render; both run on the Python that runs Copier (D81, D85). The quoted `--python '>=3.14'` makes `uvx` choose 3.14 or later; on an older Python each script changes nothing and says so in a message framed in lines of `=`.

**Why `-a`.** The answers file is called `.copier-answers.syntek-media.yml`, not Copier's default `.copier-answers.yml`, so that it can sit beside syntek-author's own. Copier only finds a non-default answers file when you name it; without `-a` it stops and changes nothing.

**Changing an answer.** Pass it on the update. A list answer replaces the whole list, so pass every value you want, for example adding TikTok:

```bash
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx --python '>=3.14' copier update --trust -a .copier-answers.syntek-media.yml \
  --data 'PLATFORMS=[youtube, tiktok, instagram, linkedin]'
```

**Removing a platform or a media kind deletes what it generated.** A value you leave out of the list loses every file it generated, seeds included, even a platform profile you have filled in — they survive only in your git history — and every file you created yourself stays: your chapter registers in `production/src/audiobook/`, your pieces, your footage.
Copy out and commit anything you need first. Every update prints, before it asks its questions, what removing each platform and each media kind deletes, workflows by full folder name.
After a change, edit by hand the files that describe your options, because an update never rewrites them: in a standalone project `README.md`, `CONTEXT.md` and `.claude/CLAUDE.md` Section 1 (over syntek-author they are syntek-author's), and any rows for a removed platform in `brand/src/platforms/overrides.toml`. The brand section of the media rules, `.claude/rules/syntek-media/01-layout-and-routing.md` Section 1, updates itself.

`BRAND_KIND` cannot change: an update that answers it differently stops before touching a file, because the mode files, the worked example and the brand seeds were written for one kind of brand. A different brand kind is a new project.

The `MissingFileWarning` about `.copier-answers.syntek-media.yml` appears on every update and is harmless, as does a second one about `.copier-answers.syntek-author.yml` in a project syntek-author has never been applied to (since 0.5.0: media reads that file for syntek-author's data-root answers and, since 0.6.0, its client and model answers).
A project that recorded `AGENT_CLIENTS: []` while it holds client files (one made before 0.5.0, standalone or over syntek-author, whose update into 0.5.0 recorded none) gets no MCP server added to them until you record its clients with `--data "AGENT_CLIENTS=[...]"` on an update.

**Migrations.** When a release moves a folder that can hold your work, or stops shipping a seed, the update runs a migration script from the template after it has written the new tree; a versioned migration, like the outside-link pair below, moves or keeps your files only where exactly one outcome is right, and never overwrites or deletes one; the family 'update' entry, the third exception below, is the one that writes over files. Media changes a shared path only through three stated exceptions (D11), two of which are keyed to no release and run on every update.
The first is 0.4.2's (D76). Earlier releases shipped `.agents` as a link to `.claude`, which makes every sandboxed Codex command fail, and Copier's update never renders a shared path. So, only where `.agents` is a link whose target is exactly `.claude`, the migration removes that link (never `.claude`), creates the real `.agents/` folder, links `.agents/skills` to `../.claude/skills`, and moves `.claude/mcp_config.json` to `.agents/mcp_config.json` where that path is free. A real folder, a link elsewhere, a text file Git checked out in place of the link, or no `.agents` is left untouched and reported, as is every tracked line that still describes the old layout. It is the first of the three. Review its report and commit; it prints the command that runs it again.
The second runs on every update and is keyed to no release (D76). Copier refuses to render anything beneath an `.agents` link that leaves the project, so where `.agents` is such a link, the update renames it to `.agents.syntek-held` before the render and back afterwards: the net change is zero, and its target is never touched. If an update stops before it ends (a refused answer, Ctrl-C at a question, or Copier failing as it cleans up after the render), the link stays held as `.agents.syntek-held`, and the next update refuses the changed tree; where the link is committed and the update stopped after its render, Copier has already put an identical `.agents` link back. Put the link back from the project root, in a POSIX shell (Terminal on macOS and Linux, Git Bash on Windows; never PowerShell's `rm`), before anything else, and before discarding the stopped update with `git reset --hard` and `git clean -fd`, which would delete a held link Git does not track. First check what stands at `.agents`: `ls -ld .agents .agents.syntek-held`. Where it shows no `.agents.syntek-held`, nothing is held: stop here and change nothing. Where `.agents` is a link (its line shows `->`), remove that link alone with `rm .agents` (never `rm -r`, never a trailing slash); where it is a folder or a file, move it aside to a name nothing holds yet (`ls -ld .agents.from-update` finds nothing) with `mv .agents .agents.from-update` (no trailing slash), which holds what the update wrote (check it, and delete nothing in it that is yours). Then, once `ls -ld .agents` finds nothing, run `mv .agents.syntek-held .agents` (no trailing slash). Never run that `mv` while `.agents` stands: it would put the held link inside it, and inside the folder outside the project where `.agents` is a link. Then update again; where `git status` still shows changes (a stop after the render), discard the stopped update first: run `git clean -n -d`, a dry run, move out of the project anything of yours it lists, then `git reset --hard && git clean -fd`. Where the held link was committed beside an identical `.agents` link, the next update moves nothing, says so, and asks you to remove the held link (`rm .agents.syntek-held`), commit, and update again. `copier update --pretend` still refuses such a project, because a pretend run skips migrations.
Those two steps run on the Python that runs Copier, which the command above asks to be 3.14 or later; on an older one they hold nothing and say so in a message framed in lines of `=`, and the update stops with `ForbiddenPathError` naming a path in `.agents`: discard it as above, then run the update again as shown (D81, D85).
The third runs on every update too, and last: the family 'update' entry, which runs the update script that ends with the report above. It does write over files: it replaces a listed shared file only where you never changed it, offers the listed entries and servers once each, and puts back over an edit or a deletion any file of the read-only guide under `how-to/`, while Git keeps your version in `HEAD` and in `refs/syntek-media/yours` (D81, D84). And 0.6.0's own migration, keyed to that release, only reports: where the guide starts, that it is read-only, syntek-author's guide or its version, `how-to` as a link, a case twin or a folder Git ignores, files of yours at the guide's paths, files under `how-to/` that no template ships, and, where `opencode.json` exists, the permissions script's `--check` and `--write` (D84). It moves nothing, and prints the command that runs it again.

**Settings and the update.** `.claude/settings.json` is a copy-only shared file, so Copier never changes it, but since 0.6.0 the update script adds, once each on Python 3.14, the entries and top-level values media's refresh data lists that the file lacks (D81). That includes the two `ask` entries for `voice remix run` that release 0.4.4 added ([the hand edits](#the-hand-edits-after-a-copy)), never one you removed after it was committed; until an update adds them, `python3 toolkit/media.py check --setup` reports each missing one as a FAIL with the line to add. The six allows stay by hand: no copy or update offers an allow. Seeds never update either: release 0.4.4 changed the Consent rule of `brand/src/voice/voice.md` (a remixed voice cites its source clone's consent ID) and the rules of `production/src/credits-log.md` (the `voice remix` row), which an older project edits by hand.
The data-root guard is never offered, by either template (syntek-author D17, D50): a settings file seeded before it shipped gains it only by hand. Add this entry to the `"PreToolUse"` list of its `"hooks"` object, beside any entry already there:

```json
{
  "matcher": "Edit|Write|MultiEdit|NotebookEdit|Grep|Glob",
  "hooks": [
    {
      "type": "command",
      "command": "bash -c 'ROOT=$(git rev-parse --show-toplevel 2>/dev/null) || exit 0; for f in \"$ROOT\"/.claude/syntek-*-dataroot.py; do [ -f \"$f\" ] && exec python3 \"$f\" guard; done; exit 0'",
      "timeout": 10
    }
  ]
}
```

**By hand, where the update script cannot run.** The next update that runs the script in full delivers what a skipped one left. Where it cannot run at all (the project is a folder inside another Git repository, not its own; `.claude/settings.json` or an MCP file is a link, lies beyond one, or is ignored by Git; or a write fails), render the release your answers file records into a temporary folder from your own answers, then copy across only what you lack, from the project root:

```bash
T="$(mktemp -d)/media"
REF="$(sed -n 's/^_commit: //p' .copier-answers.syntek-media.yml)"
uvx --python '>=3.14' copier copy --trust --defaults --vcs-ref="$REF" --data-file .copier-answers.syntek-media.yml \
  gh:Syntek-Dev/syntek-media "$T"
for f in .claude/hooks/CONTEXT.md .claude/hooks/CLAUDE.md .claude/hooks/pre-compact-handoff.sh \
    .claude/hooks/context-threshold-handoff.sh .claude/hooks/how-to-read-only.sh handoffs/CONTEXT.md handoffs/CLAUDE.md \
    .claude/skills/{grill-me,grill-with-docs,grilling,handoff,to-questionnaire,wait-what,wayfinder}/SKILL.md \
    how-to/{,docs/,src/,src/TEMPLATE-GUIDE/,workflows/}{CONTEXT,CLAUDE}.md \
    how-to/src/TEMPLATE-GUIDE/{agent-clients-and-mcp,the-data-root,updating-and-recovery}.md; do
  [ -e "$f" ] || { mkdir -p "$(dirname "$f")" && cp -p "$T/$f" "$f"; }
done
git status
```

The loop never replaces a file you have, and `cp -p` keeps each hook's mode 755. Then add by hand to `.claude/settings.json` what `"$T/.claude/settings.json"` holds and yours lacks, the data-root guard among it. Compare `.mcp.json` with the temporary copy's and take its two servers if you want them; with the code-review-graph server, also add the line `/.code-review-graph/` to your `.gitignore`, as `"$T/.gitignore"` has it, so that Git ignores the graph's database. A coding agent's files come from the bridge's steps, `.claude/syntek-media-agents.md`, after you record the client with `--data "AGENT_CLIENTS=[...]"` on an update.

Commit `.copier-answers.syntek-media.yml` and never edit it by hand; it is the record every future update merges against.

## Living beside syntek-author

syntek-author was built to share a repository with a second template, and syntek-media is that template. Seven rules make sharing safe, and media keeps each. A combined project needs syntek-author v0.6.0 or later, updated before media:

1. Each template records its answers in its own file — this one's is `.copier-answers.syntek-media.yml`.
2. Each template keeps its instructions in its own folder, `.claude/rules/<template>/`. No template updates `.claude/CLAUDE.md`, which stays yours. Media's eight rules files load at launch beside syntek-author's, and the brand brief lives in the first of them, so it updates with the answers.
3. The shared files are written by whichever template comes first. Media's fifty shared paths are copy-only, so Copier never renders one on update, and one you delete stays deleted outside `how-to/`. Thirty-nine of them are syntek-author's family-shared files — the working-practice skills, the hooks with their pair, the `handoffs/` pair, the client files, `.mcp.json` and the user guide's shared files — which both templates ship byte for byte the same, so a combined project holds one copy whichever came first (D80, D84). Since 0.6.0 each template's update script, as syntek-author's does, refreshes the listed family-shared files you never changed from its own render history, and adds the listed settings entries and the two MCP servers once each, whichever template's script reaches them first (D81). Media's own ignore rules live in nested `.gitignore` files inside its own folders.
4. Skill and layer names never collide. The writing skills ship only from syntek-author; the seven working-practice skills, the hooks with their pair, the `handoffs/` pair, the client files and, since 0.6.0, the shared files of the user guide and its guard ship from both, byte for byte, and media's own mode files beside five of the skills are named `MEDIA-<KIND>.md`, so they never meet syntek-author's. In `how-to/` each template keeps its own files under its own `syntek-media/` or `syntek-author/` folders, and neither template's update ever downgrades the other's version of a shared file: it keeps it and reports it. The names media must never take are frozen in `.github/scripts/syntek-author-names.txt`, which two audits read on every run.
5. Large binaries never sit in plain Git: renders and generated audio are ignored, footage and approved takes live in external storage, and Git LFS holds only large design exports.
6. One project, one data-root layout. The data-root questions are the family's, so a first answer defaults to syntek-author's recorded one and must equal it, and a later difference is reported after the update; both templates' data commands refuse while the two records disagree (D14, D80).
7. One project, one set of agent clients and models. Since 0.6.0 the client and model questions default to the project's own record, then syntek-author's, so media applied second writes no client file syntek-author left out, both model tables follow the same answers, and media's update script adds each family server only once to those clients' existing files (D81).

Apply each template with its own answers file and update each separately, syntek-author first. Copier refuses to update a repository with uncommitted changes, so each command starts from a clean, committed tree:

```bash
uvx --python '>=3.14' copier copy --trust gh:Syntek-Dev/syntek-media .
git add -A && git commit -m 'Apply syntek-media'
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx --python '>=3.14' copier update --trust -a .copier-answers.syntek-author.yml
git add -A && git commit -m 'Update from syntek-author'
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx --python '>=3.14' copier update --trust -a .copier-answers.syntek-media.yml
git add -A && git commit -m 'Update from syntek-media'
```

The other order works too — media first, then syntek-author, both without `--overwrite` — but choose syntek-author first where you can. Whichever template comes first writes the shared files, and media's leave out what syntek-author needs. syntek-author prints no message after its copy, so in the media-first order add these by hand from syntek-author's own template files, then commit (only the allows and the ignore rules remain):

- **`.claude/settings.json`:** its allows `Bash(make *)` and `Bash(python3 tooling/*.py *)`, plus `Bash(sqlite3 tooling/references.db *)` or `Bash(uv run tooling/font.py *)` where its references or constructed-language options are on. Keep media's own entries. syntek-author's copy, run on Python 3.14, adds its own denies to media's settings file once, as its `baseline` task adds every entry its refresh data lists: `Edit(**/*.pdf)` and `Edit(build/**)`, plus `Edit(typeset/src/units/.base/**)` outside a business project. Media's seed already carries syntek-author's `hooks` object (the four handoff-hook entries, then the data-root guard and the guide guard), `idleCompaction` and `autoCompactEnabled`, its Scrapling and code-review-graph asks and its `AskUserQuestion` and `embed_graph_tool` denies, byte for byte.
- **`.gitignore`:** the sections media's copy does not carry: its build output (`/build/`); its SQLite sidecars (`*.db-journal`, `*.db-wal`, `*.db-shm`); its Word and LibreOffice lock files (`.~lock.*#`, `~$*.docx`, `~$*.xlsx`, `~$*.pptx`); and its TeX intermediates (`*.aux`, `*.log`, `*.out`, `*.toc`, `*.fls`, `*.fdb_latexmk`, `*.synctex.gz`, `*.xdv`). Check with `git check-ignore build/x.pdf`.
- **`README.md`, `CONTEXT.md`, `.claude/CLAUDE.md` and `.claude/CONTEXT.md`** describe media only. Optionally add syntek-author's layers and its rules folder, `.claude/rules/syntek-author/`: its rules load at launch whatever these files say, and media's `.claude/CLAUDE.md` already defers to its project settings file.

In a combined project:

- **syntek-author's project settings file outranks media's rules.** Where `.claude/rules/syntek-author/00-project.md` is present, media reads it at run time, never through Copier: its Paths say where project rules and handoffs go, its Memory headings map the headings of `.claude/MEMORY.md`, a Workflow aliases row may name a media workflow by its full folder path, and an Overrides row may name a media rules file and section.
- **Two routers, two kinds of work.** syntek-author's router never sees media's layers. Media's own, `run-media-workflow`, routes video, audio, captions, thumbnails and posting, and leaves writing work to syntek-author's router, where present.
- **The social-media family owns the written social plan.** In a business project with syntek-author's social-media family (on by default), its documents own the social media plan, the content calendar, the bios, the channel voice and text-only posts. Media's platform profile then holds only delivery facts, its schedule lists only media deliverables, each citing its calendar entry, and its post packages cite the entry too.
- **The writing skills are companions.** Media runs spelling, grammar, comprehension, flow and fact-check on scripts, transcripts and post copy as reports, and improve-section and adapt-section on a script only as a report followed by the edits you agree, with no ledger entry: the provenance ledger belongs to syntek-author's content layer.
- **The skills signposts are syntek-author's.** `.claude/skills/CONTEXT.md` lists syntek-author's roster and calls any other skill your own; media's skills are listed in `.claude/rules/syntek-media/02-skills.md` and are template-owned by syntek-media.
- **`make flags` and `make lint` read media's `src/` Markdown too**, so media's scripts, registers and plans are written one sentence per line. From syntek-author v0.6.0 they read `how-to/src/` only under `SCOPE=how-to/src`, where media's chapters report nothing.
- **Two user guides, one folder.** `how-to/` holds both templates' guides, each under its own `syntek-media/` or `syntek-author/` folders, and the three shared chapters once. Both are read-only, and each template's update puts back only its own files and the shared ones. syntek-author's `run-workflow` reads only `how-to/workflows/syntek-author/`, and media's procedures are run as their folders say, never routed.
- **syntek-author's own audits run on a syntek-author-only render.** Its `doc-references.sh` stays clean on a combined tree, but its `skill-conformance.sh`, `shipped-variants.sh` and `docs-pairing.sh` flag media by design: media's skills are outside its catalogue, a mode file sits on a skill it treats as unmoded, and its `docs-pairing.sh` does not know media's `generated/`, `renders/` and `raw/` folders, which carry only a `README.md`.
- **Hand off, never compact.** The handoff skill and its two hooks ship with both templates, byte for byte (D80); `.claude/settings.json` sets `autoCompactEnabled` and `idleCompaction` false, and after a deliberate `/compact` the `SessionStart` `compact` entry says that a handoff gives a cleaner break. The handoff goes in the folder syntek-author's Paths give, or in `handoffs/` in a standalone project.

## Large files: renders, audio and footage

Big binaries never sit in plain Git. Each kind of large file has one home:

- **Renders and generated audio are ignored.** Every `renders/` and `generated/` folder keeps only its `README.md` in Git; masters, cuts, card and thumbnail PNGs, takes and audiobook chunks are ignored by nested `.gitignore` files that ship in every project, whatever platforms and media kinds you chose. Each piece's output sits in a folder named for it inside `production/src/renders/`, `production/src/voiceover/generated/` (its takes in `takes/`) and `publishing/src/renders/`, ignored whole; a piece's tracked timing and scene files stay flat, under its name, in `production/src/timing/` and `production/src/scenes/`. A render is regenerable from tracked files.
- **Source footage lives in external storage, by decision.** Every recorded or licensed source file — camera footage, recorded audio, music beds, stock — has a row in `production/src/footage/manifest.toml` (path, sha256, size, duration, and a label for where the master copy lives), and a local mirror in the ignored `production/src/footage/raw/`. `python3 toolkit/media.py footage add` copies a file into the mirror (it never moves one) and hashes it; `footage verify` proves the mirror matches the manifest. Footage is large and rarely diffed, it would exhaust LFS storage and bandwidth quotas, and the checksums keep every edit reproducible.
- **Approved generated audio is archived the same way.** A take cannot be made again — regenerating it spends credits and gives a different take — so an approved take or mastered chapter is logged with `footage add --kind generated` before the piece is produced. For an audiobook the approved mastered chapter is what must be kept; its chunk takes may be, on your word.
- **Git LFS holds only large design exports**, in `brand/src/exports/large/`, through a nested `.gitattributes` that exempts itself and the folder's pair. Small exports are committed in `brand/src/exports/`. Never add a root `.gitattributes` and never run `git lfs track`, which writes one: it would be a shared root file neither template seeds.
- **Two guards.** Without a configured LFS filter, git commits an LFS-marked file whole, silently. The copy's tripwire sets `filter.lfs.required` where no filter is configured, so that `git add` fails loudly instead, and `python3 toolkit/media.py check` reports LFS-marked files stored as plain blobs, LFS-marked files with no filter configured, and any file over 10 MB outside the ignored and LFS folders.
- **The data root files nothing of media's yet.** The family can keep a project's binaries outside the repository, under each machine's data root (`DATA_STORE` external; see [The questions](#the-questions)). Media's map, `.claude/syntek-media-dataroot.json`, names no folder yet (D80), so footage, takes and exports stay as above whatever the answer. Its resolver, `python3 .claude/syntek-media-dataroot.py root`, reports the root and the answers, and the data-root guard in the settings seed keeps the session's file tools out of the root. Where media's answers and syntek-author's differ, the update says so, and the data commands refuse until they agree.

## Audio with ElevenLabs

The voiceover, narration and captions skills generate audio and transcripts through an ElevenLabs MCP server named `elevenlabs`. They only call it when you ask; before any call they state the characters or audio minutes, the number of calls and the estimated credits, and wait for your yes; they make one call at a time; and every spend gets a row in `production/src/credits-log.md`.

The template adds **no ElevenLabs server** to the project's `.mcp.json`, which holds only Scrapling and code-review-graph. Add the server once, at **user** scope, so it is available to every project on your machine and its key lives in your own Claude Code configuration (`~/.claude.json`), never in a repository.
**Its base path must contain the project.** The server saves every file under `ELEVENLABS_MCP_BASE_PATH` (default `~/Desktop`) unless a skill passes an absolute folder, which media's skills always do, and it refuses to read any input file outside that path — so with the default, speech-to-text rejects every project file with 'outside of allowed directory'. The path is resolved before the test, so a symbolic link does not help.
Use `$HOME` when every project lives under it; otherwise the nearest folder that holds them all, such as the disk your repositories live on. An existing server, syntek-author's included, is removed and added again:

```bash
claude mcp remove elevenlabs --scope user
claude mcp add --env ELEVENLABS_API_KEY="$ELEVENLABS_API_KEY" --env ELEVENLABS_MCP_BASE_PATH="$HOME" \
  --transport stdio --scope user elevenlabs -- uvx elevenlabs-mcp
```

Replace `"$HOME"` with that folder where your projects live elsewhere; when the error appears, the `captions` skill prints the exact command with a base path it has computed to contain the project.
Export the key in your shell first rather than typing it on the command line, and never commit it. The server must be named `elevenlabs`: the skills call its tools by that name (`mcp__elevenlabs__text_to_speech`).

- **Permissions.** The server marks every tool read-only, so a project's `.claude/settings.json` asks before each of the nine tools that spend credits and before `voice remix run`; over syntek-author, the copy's `baseline` task adds those `ask` entries on Python 3.14, and you add them by hand only where it did not run ([the hand edits](#the-hand-edits-after-a-copy)). `python3 .claude/syntek-media-permissions.py --write` then carries them to Gemini CLI's and OpenCode's files (see [Using other coding agents](#using-other-coding-agents)).
- **Character voices.** The workflow `production/workflows/11-design-character-voices/`, in every brand kind, designs a character's voice from your own cloned voice: it drafts a description from the manuscript or script, `python3 toolkit/media.py voice remix plan` shows the one call first, and `voice remix run --approve-call` sends it straight to ElevenLabs with the `ELEVENLABS_API_KEY` exported in your shell, saving the previews as a voice trial. You listen and choose; the chosen preview is saved through the server (`mcp__elevenlabs__create_voice_from_preview`) and recorded in `brand/src/voice/voice.md` under the consent of the voice it came from. Remix accepts only a voice your account created, never a Voice Library voice. One voice per take for now: a piece that switches voice between segments is not supported yet.
- **The model** is discovered with `mcp__elevenlabs__list_models` and recorded per use in `brand/src/voice/voice.md`, never assumed.
- **Voiceover** is made one segment per spoken sentence or beat, so the captions can be timed from the segments' own durations at no cost.
- **Output formats.** The skill chooses the format for the deliverable and says when it needs a higher ElevenLabs plan: `mp3_44100_192` needs Creator or above, and `pcm_44100` Pro or above.
- **Audiobooks** have no script: the chapter register, with its opening and closing credits, is the plan you approve first. They have three routes, chosen per channel with you. ACX and Audible need a human narrator unless you are authorised otherwise; an AI master through the server goes only to channels that accept one; and a channel that takes only ElevenLabs' own package is made in ElevenLabs' studio, outside this template.
- **Disclosure.** Every piece with a synthetic voice — your own cloned voice included — records it in its brief. At publish, each platform's AI label is set exactly when that platform's rule requires it, and a disclosure line goes in every description.
- **Without the server**, `espeak-ng`, where installed, makes a scratch track for timing, labelled approximate.

## Design with Claude Design

Visual design happens in Claude Design, in one design-system project per brand.
The repository holds the source of truth: `brand/src/design-system/tokens.css` (the CSS custom properties every layout imports), the brand's fonts, and preview cards whose first line, `<!-- @dsCard group="…" -->`, files each card in the Design System pane.
Two of those cards are the brand's own layouts — `previews/thumbnail.html` and `previews/card.html` — which every new piece's thumbnail and title card is copied from, so a layout changed in Claude Design and synced reaches every later piece.
You start the sync, with `/design-sync`, and it works one component at a time, never a wholesale replace (the workflow `brand/workflows/02-sync-with-claude-design/`). Its converter expects a React kit, so the first sync of this plain HTML kit is checked by hand; `/design import` and `/design export` are the fallback route.
Each exported design is recorded in `brand/src/design-register.md` with its Claude Design link and where the export is kept. There is no design editor, no React and no Node in the project.

## Using other coding agents

Claude Code's `.claude/` tree is canonical and always ships. A copy also writes the files of the coding agents ticked in `AGENT_CLIENTS` (all four on a fresh standalone copy; over syntek-author, the clients its answers file records), each only where it does not already exist (D80, syntek-author D47):

| Client      | Its files                                                                 |
| ----------- | ------------------------------------------------------------------------- |
| Codex       | `AGENTS.md`, `.codex/config.toml` and the `.codex/` pair                  |
| Gemini CLI  | `GEMINI.md`, `.gemini/settings.json` and the `.gemini/` pair              |
| Antigravity | `GEMINI.md` and `.agents/mcp_config.json`                                 |
| OpenCode    | `AGENTS.md` and `opencode.json`                                           |

Any of them also gets a real `.agents/` folder holding the relative link `skills -> ../.claude/skills`. `.agents` is never itself a link: Codex mounts it read-only, and its sandbox refuses a read-only link to a writable folder (D76). These files are syntek-author's, byte for byte, so a combined project receives the same ones whichever template comes first. Every client reads the template-owned `.claude/syntek-media-agents.md`, and every other `.claude/syntek-*-agents.md` present, which route to the canonical rules, project memory, folder pairs, skills and mode files. Local and project-specific rules still win.

A model you name in `CODEX_MODEL`, `GEMINI_MODEL` or the `OPENCODE_*` answers is written into that client's file by the copy, and the tier it serves is a row in the model table of `.claude/rules/syntek-media/05-model-allocation.md`; change the client's file by hand later. Codex's `.codex/config.toml` enables `CLAUDE.md` as a fallback instruction filename once the project is trusted, and sets no trust level, permission bypass or credentials. The Opus and Sonnet labels in workflows identify work tiers on other clients; a capability unavailable in a client needs the documented manual route.

**MCP servers.** `.mcp.json` and each client's own file carry two servers, pinned and keyless: `scrapling` (web pages) and `code-review-graph` (a local map of the code). The ElevenLabs server is never among them: it is added at user scope (see [Audio with ElevenLabs](#audio-with-elevenlabs)). Use them as `.claude/rules/syntek-media/06-global-rules.md` Section 13 says: ask before each of Scrapling's six browser tools, and never run `code-review-graph install` or `scrapling install`. Codex and Gemini CLI start them only in a trusted project; OpenCode starts them when it opens the project and runs every tool the project does not ask for without a prompt. The first start downloads them through `uvx`. Since 0.6.0 the copy's `baseline` task and every update add the two servers, once each, to `.mcp.json` and the existing MCP files of the clients the answers record, and to `opencode.json` and `.gemini/settings.json` only once `python3 .claude/syntek-media-permissions.py --write` has given them every ask form the servers' tools need (D81); a server you removed after it was committed is never added back.

**Permissions in every client.** `.claude/settings.json` holds the project's ask and deny rules, the ElevenLabs asks among them. After a copy, and whenever you change those rules, carry them to the other clients' files that exist:

```bash
python3 .claude/syntek-media-permissions.py --check    # what is missing, and what a client cannot express
python3 .claude/syntek-media-permissions.py --write    # adds the missing rules; never creates a file
```

It never writes an allow rule, never removes or reorders one, and prints what to set by hand where a client cannot express a rule (Antigravity's settings are set in the app).

**Existing projects:** Copier's update never adds or recreates a client's files, and the update script changes one only by adding those two servers once. Record the clients you use with `--data "AGENT_CLIENTS=[...]"` on an update, then follow the bridge's explicit setup, step by step in `how-to/workflows/syntek-media/06-enable-a-coding-agent-client/`: generate a separate temporary project using the recorded source, ref and answers, review its client files, and copy only missing files. Preserve existing instructions and settings; agree a pointer to the bridge in an existing entrypoint. Updating across 0.4.2 replaces an `.agents -> .claude` link with the real folder; preserve any real `.agents` directory or differently targeted link and resolve its integration manually. An `.agents` link to a folder outside the project is held aside and restored by every update; a copy over one needs the hand recipe at the top of this guide. On Windows, Git may check `.agents/skills` out as a text file (`core.symlinks=false`); the bridge says how to recreate the link. Never re-run a template copy with overwrite on the real project.

The template development repository has separate root entrypoints and a Codex config that
disables every product skill. Its `.agents/` is a real folder holding only its pair; it exposes no skill.

## Working on the template

Read [`DESIGN.md`](DESIGN.md) first: it is the build contract, and where any other file disagrees with it, `DESIGN.md` wins. [`CONTEXT.md`](CONTEXT.md) maps this repository, and `.claude/CLAUDE.md` is the development manual — token discipline, how to add a skill, a mode file, a gated path, a platform or a media kind, and what to run before committing. Changes are recorded in [`CHANGELOG.md`](CHANGELOG.md). To propose a change, start with [`CONTRIBUTING.md`](CONTRIBUTING.md); report a vulnerability only as [`SECURITY.md`](SECURITY.md) says.

Scene pieces use `production/docs/reference/scenes-as-code.md` and
`production/workflows/10-animate-a-scene/`: review first/middle board stills with
`uv run toolkit/scene.py stills`, then render each aspect natively with `scene.py render`.
The kit computes every frame in Python; Playwright draws only local brand art and indexed
captures. `--memory-max SIZE` or user-scope `MEDIA_MEMORY_MAX` optionally caps assemble and
scene renders under systemd with swap disabled; other runs report that they are uncapped.
No scene command calls a generation API.

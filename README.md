# syntek-media

**A Copier template that adds audio and video production to a repository — brand, scripts, production and publishing layers, a small ffmpeg toolkit and a Claude Code skill suite — for a business or an author.**

![Version](https://img.shields.io/badge/version-0.5.0-blue)
[![Licence: MIT](https://img.shields.io/badge/licence-MIT-green.svg)](LICENSE)
![Template: Copier](https://img.shields.io/badge/template-copier-blue)

```bash
uvx copier copy --trust gh:Syntek-Dev/syntek-media .
```

Copier asks its questions, renders the layers for the brand kind, platforms and media kinds you choose, writes the files of the coding agents you tick, runs `git init` where no repository exists, makes the hooks in `.claude/hooks/` executable, and sets a Git LFS tripwire where no LFS filter is configured.
Before copying into an existing project, check `.agents`. If it is a symbolic link (`test -L .agents`), such as `.agents -> .claude`, add `--exclude /.agents` to the copy command, then make the real folder as the bridge, `.claude/syntek-media-agents.md`, says. If `.agents/skills` is a real directory (`test -d .agents/skills && test ! -L .agents/skills`), preserve it and add `--exclude /.agents/skills`; integrate its skills manually afterward. A `.agents/skills` link, whatever its target, needs no exclude: Copier skips it and leaves it as it is. Without the exclude Copier stops with an `AssertionError` before its skip check, because a path that resolves to a directory meets a link in the template. Fresh projects receive a real `.agents/` folder holding `skills -> ../.claude/skills` and `mcp_config.json`; updates never write under `.agents` (D76).
If `.agents` is a link to a folder outside the project, Copier refuses to render anything beneath it, `--exclude` included, so move the link aside for the copy and put it back: `mv .agents .agents.syntek-held`, copy with `--exclude /.agents`, then `mv .agents.syntek-held .agents`. The link's target is never touched; updates do the same for you (see Migrations, below).
It is built to be applied inside a project generated by syntek-author, beside its writing layers, and it also renders on its own into an empty folder.

## What it generates

One template, three brand kinds. You choose the kind once, with `BRAND_KIND`, and it cannot be changed later.

| Brand kind          | For                                                                 | Applied over syntek-author's | What is particular to it                                                                                                                                                                        |
| ------------------- | ------------------------------------------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `business`          | A business's social video, recorded talks and explainers            | `business`                   | Business mode files; where syntek-author's social-media family is present, it owns the written social plan, the content calendar and the bios, and media's profiles, schedule and posts cite it |
| `author-fiction`    | A novelist's book trailers, audiobook and author socials            | `fiction`                    | Fiction mode files: trailers built from stills, cards, fades and push-ins; the spoken form of constructed names; audiobook narration from the promoted manuscript                               |
| `author-nonfiction` | A non-fiction author's talks, podcast, audiobook and author socials | `theology`                   | Non-fiction mode files: recorded talks cut into clips and podcast episodes; quotation and scripture-translation permissions for audio as worked examples; the audiobook                         |

Every brand kind shares the same spine:

- **The piece and its ladder.** One deliverable work — a short, an explainer, a talk, a trailer, a podcast episode, an audiobook, a standalone voiceover — lives in `scripts/src/pieces/NNN-kebab-title/` and moves from `idea` to `published` through seven gates, M1 to M7, defined in `scripts/docs/reference/the-piece-ladder.md`. A recorded talk enters with an approved transcript instead of a script, and an audiobook with an approved chapter register.
- **Production layers.** `brand/` (the visual tokens and layouts, the spoken voice, one profile per platform), `scripts/` (briefs, scripts, transcripts, storyboards and shot lists), `production/` (the footage manifest, voiceover, word and mouth timings, scene files, edit decision lists, cards, masters, rights and credits) and `publishing/` (cut-down plans, captions, thumbnails, post packages, the schedule and the publish log), each with reference guides in `docs/reference/`, numbered workflows and a place for your own procedures. **A supporting layer**, `toolkit/`, holds the production code.
- **The production code.** One standard-library command line, `python3 toolkit/media.py`, drives ffmpeg for masters, cuts, encodes, loudness, captions and burn-in, images (JPEG, WebP, AVIF, posters) and GIF previews, and writes a self-hosted podcast's RSS feed with the standard library; `uv run toolkit/card.py` renders the brand's HTML and CSS layouts to PNG thumbnails and cards with a pinned Playwright. Platform limits are dated data in `toolkit/data/platforms.toml`, never numbers in a guide. Every output a piece makes lands in a folder named for it, and `python3 toolkit/media.py where <piece>` lists the piece's tracked files and names those folders.
- **Audio.** ElevenLabs voiceover, narration and speech-to-text through your user-scope MCP server: never unasked, the cost stated first, one call at a time, every spend logged.
- **Design.** The brand's tokens and its thumbnail and card layouts live in `brand/src/design-system/`, kept in step with its Claude Design project by `/design-sync`, which you start, one component at a time.
- **Claude Code configuration.** Skills only, no agents; the rules in `.claude/rules/syntek-media/`; hand off, never compact.

Platforms and media kinds add to a brand kind. Each is a multiple choice, and every brand kind is offered every value:

| Platform     | On by default for                     | Adds                                                                                                                                                                                                                                                  |
| ------------ | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `youtube`    | every brand kind                      | `brand/src/platforms/youtube.md` (your profile, a seed) and `publishing/docs/reference/youtube.md` (limits by data key, the disclosure setting, captions, thumbnails, the platform's traps)                                                           |
| `tiktok`     | `author-fiction`                      | the same two files for TikTok                                                                                                                                                                                                                         |
| `instagram`  | every brand kind                      | the same two files for Instagram                                                                                                                                                                                                                      |
| `linkedin`   | `business`                            | the same two files for LinkedIn                                                                                                                                                                                                                       |
| `facebook`   | `author-fiction`, `author-nonfiction` | the same two files for Facebook                                                                                                                                                                                                                       |
| `podcast`    | `author-nonfiction`                   | the same two files for Apple Podcasts and Spotify, and, for a show you serve yourself, `publishing/docs/reference/podcast-feed.md`, `publishing/workflows/08-publish-the-podcast-feed/` and `publishing/src/podcast/` (your show registers and feeds) |
| `website`    | none                                  | `brand/src/platforms/website.md` (your sites, each with its agreement where you do not own it) and `publishing/docs/reference/website.md` (self-hosted or embedded video, posters, share images, captions and transcripts, the hosting tests)         |
| `blog`       | none                                  | the same two files for blog posts: the video, its transcript, featured and share images                                                                                                                                                               |
| `newsletter` | none                                  | the same two files for email issues: a linked preview image or GIF, never video (your lists, never a subscriber)                                                                                                                                      |

**One `website` platform covers every site** you publish media to, your own and any you write for: each site is a row of your website profile, named by a slug, and one render serves every page that uses its key. Media makes the files and the few words outside the page (alt text, an embed's title, the structured-data values); the page, post or issue itself, its words and its date are the written side's, syntek-author's where it is present. Media never edits a website, sends an email or holds a subscriber list.

**Self-hosting a podcast.** A podcast can go to Apple Podcasts, Spotify and YouTube and be served from your own website or websites. A show you serve yourself has one RSS feed, written by `python3 toolkit/media.py feed` from its show register and uploaded by you, with the episode audio, art, captions and chapters, to one site you own; Apple Podcasts and Spotify read that feed, and YouTube takes each episode as video, uploaded into the show's podcast playlist. An episode reaches the feed by one of two routes: a talk published whole as an episode (one piece, its `youtube.long` and its `podcast.feed_audio` from one master; `MEDIA_KINDS` needs only the talk's own kind) or an episode of its own (a `podcast` piece, mastered by the podcast-episode workflow; `MEDIA_KINDS` needs `podcast`). A page on another site that plays the episode is a placement with its own agreement, never a second feed. A show kept on a podcast host instead delivers `podcast.apple_rss_audio` to the host and uses neither the register nor the feed workflow. Choose `podcast` for either, and `website` beside it for episode pages on your own site.

| Media kind    | On by default for                     | Adds                                                                                                                                                                                                               |
| ------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `short-video` | every brand kind                      | `scripts/docs/reference/short-video.md`                                                                                                                                                                            |
| `long-video`  | `business`, `author-nonfiction`       | `scripts/docs/reference/long-video.md`                                                                                                                                                                             |
| `podcast`     | `author-nonfiction`                   | `scripts/docs/reference/podcast-episodes.md` and `production/workflows/04-master-a-podcast-episode/`                                                                                                               |
| `audiobook`   | `author-fiction`, `author-nonfiction` | the `narrate-audiobook` skill, `production/src/audiobook/`, `production/workflows/05-narrate-an-audiobook/`, `production/workflows/06-master-an-audiobook/` and `production/docs/reference/audiobook-narration.md` |
| `trailer`     | `author-fiction`                      | `scripts/docs/reference/trailers.md`                                                                                                                                                                               |
| `voiceover`   | every brand kind                      | `scripts/docs/reference/standalone-voiceovers.md`, the guide to a piece that is only a voiceover. The `voiceover` skill, its workflow and its folder ship whatever you choose                                      |

`SEED_EXAMPLES` adds one worked example piece, once.

The writing skills — spelling, grammar, comprehension, flow, fact-check, improve-section, adapt-section and research — come from syntek-author and are never shipped here.
Media's files name each one as a companion, 'the spelling skill (syntek-author), where present', and its skills check that the companion exists before they use it.
The seven working-practice skills — `grilling`, `grill-me`, `grill-with-docs`, `wayfinder`, `handoff`, `to-questionnaire` and `wait-what` — ship with both templates, byte for byte the same (D80).

## Requirements

Scene rendering uses the same pinned Playwright/Chromium as cards; systemd memory caps are optional.

| Tool                                                   | Needed for                                                                                                                                                                                                                                                             |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [uv](https://docs.astral.sh/uv/) (`uvx`)               | Running Copier without installing it (Copier 9.12.0 or newer), and `uv run toolkit/card.py`.                                                                                                                                                                           |
| git 2.31 or later                                      | Every project is a repository; updates are three-way merges, and the update script reads the Git history of the files it updates.                                                                                                                                                                                                         |
| Python 3.14 or newer                                   | The standard-library `media.py` toolkit, the session hooks and every update (Copier run as `uvx --python '>=3.14' copier`); author data is TOML and generated timing is JSON. Optional dependency workers are described below. Also the data-root and permissions scripts in `.claude/` (`syntek-media-dataroot.py`, `syntek-media-permissions.py`).                                                                                                                 |
| ffmpeg and ffprobe                                     | Masters, cuts, encodes, loudness and burned-in captions. Built with libass, x264 and mp3lame. With libwebp, an AV1 encoder (libaom-av1 or libsvtav1) and the `avif` muxer (optional), `media.py image` also writes WebP and AVIF images; `check --setup` reports them. |
| Playwright's Chromium                                  | Thumbnails and cards rendered to PNG. Install it once with `uv run --with playwright==1.63.0 playwright install chromium`, or use a system bundle at the same revision (NixOS); nothing is installed globally.                                                                                                              |
| git-lfs                                                | Large design exports in `brand/src/exports/large/`, and nothing else.                                                                                                                                                                                                  |
| espeak-ng (optional)                                   | An offline scratch voice for timing a script, labelled approximate.                                                                                                                                                                                                    |
| An ElevenLabs MCP server named `elevenlabs` (optional) | Voiceover, narration and speech-to-text, added at user scope (see [Audio with ElevenLabs](#audio-with-elevenlabs)).                                                                                                                                                    |
| syntek-author (recommended)                            | The writing skills and the project settings file. Media works without them, with less; the handoff skill and the other working-practice skills ship with both templates.                                                                                                                                                              |
| Codex, Gemini CLI, Antigravity or OpenCode (optional)  | Other coding agents, each reading the same rules, skills and memory through the bridge, `.claude/syntek-media-agents.md`. A copy writes the files only of the clients ticked in `AGENT_CLIENTS` (see [Using other coding agents](#using-other-coding-agents)). |
| The `scrapling` and `code-review-graph` MCP servers (optional) | Web pages, and a local map of the code. Both are pinned and keyless in `.mcp.json` and each client's own file, and start through `uvx`; the first start downloads them, and Scrapling drives Playwright's Chromium. |
| [Claude Code](https://code.claude.com/)                | The skills, rules and workflows.                                                                                                                                                                                                                                       |

In a generated project, `python3 toolkit/media.py check --setup` reports the toolkit's own tools in this table (uv, Python, ffmpeg and ffprobe, Playwright's Chromium, git-lfs, espeak-ng and the ElevenLabs server), and the ElevenLabs permissions and base path, without changing anything. It never looks for syntek-author, the other coding agents or the `scrapling` and `code-review-graph` servers, and of the settings entries it reports media's own only.

Optional word alignment uses `toolkit/transcribe.py` (Python >=3.10,<3.14, WhisperX 3.8.6), launched through `media.py transcribe` under `MEDIA_TRANSCRIBE_PYTHON` at user scope or offline uv. The author runs `python3 toolkit/media.py transcribe fetch` once for English wav2vec2 weights, nltk's punkt_tab and the cross-check model; skills and audits never fetch them or build the WhisperX environment. Author-edited data is TOML; tool-written timing is finite JSON. Captions can follow accepted word timings with `captions from-words`, preserving the first and last word of each cue.

## Applying to a syntek-author project

syntek-media is built to be applied inside a project generated by syntek-author — a business document library, a novel or a theology book — with its own answers file beside syntek-author's.
Apply syntek-author first, then media: a `business` project takes `business`, a `fiction` project `author-fiction`, a `theology` project `author-nonfiction`.
Nothing moves: every folder media adds is new, and every root file the two templates share is already there and is left exactly as it is.

1. **Start from a clean, committed tree, on a branch.**

   ```bash
   git switch -c apply-syntek-media
   ```

2. **Copy the template into the project**, answering the questions, or with an answers file you have edited from `examples/`:

   ```bash
   uvx copier copy --trust gh:Syntek-Dev/syntek-media .
   ```

   ```bash
   cp /path/to/syntek-media/examples/business.answers.yml /tmp/answers.yml   # then edit every value
   uvx copier copy --trust --data-file /tmp/answers.yml \
     --data SEED_EXAMPLES=false gh:Syntek-Dev/syntek-media .
   ```

   In your copy of the example, delete the `DATA_*` lines wherever syntek-author records its own (every syntek-author project from its v0.5.0 does): media then takes syntek-author's data-root answers, and a first answer that differs is refused, because one project keeps one store.
   The coding-agent answers are different: media never reads them from syntek-author's answers file, and on a first copy `AGENT_CLIENTS` defaults to all four clients. So answer `AGENT_CLIENTS` and the model questions (`CODEX_MODEL`, `GEMINI_MODEL` and the `OPENCODE_*` keys) as `.copier-answers.syntek-author.yml` records them: in your copy of an example, set those lines to syntek-author's, or pass them with `--data`, such as `--data 'AGENT_CLIENTS=[codex]'`. Otherwise the copy writes the files of every client media's answer ticks that the project lacks, those of clients syntek-author's answers left out included, and media's model table in `.claude/rules/syntek-media/05-model-allocation.md` lists clients syntek-author's does not.
   To apply from a local clone instead, replace `gh:Syntek-Dev/syntek-media` with the clone's absolute path, such as `"$(realpath ../syntek-media)"`, and add `--vcs-ref=HEAD` (see [Generating a standalone project](#generating-a-standalone-project)).
   **Never pass `--overwrite`.** Copier leaves existing shared files alone, printing each as `conflict` then `skip` (or as `identical`, where the two copies match). That pair is expected and is not a collision; missing shared paths are filled by media.
   Any other path that already exists is a collision, which is a template bug: a non-interactive copy stops with 'Interactive session required' before it writes that file, and an interactive one asks 'Overwrite …?' with yes as the default — answer no.
   Either way, `git status` shows anything written before the stop; remove it and report the collision.

3. **Review `git diff`, then make the hand edits** below, which the shared files cannot learn from a copy that skipped them.

4. **Commit**, including `.copier-answers.syntek-media.yml`. From here, each template updates separately (see [Updating a project](#updating-a-project)).

There are no adoption scripts.
Every media folder is new, so no move has exactly one right destination, and loose media already in the repository — old footage, a folder of social clips — is yours to sort.

### The hand edits after a copy

The copy prints these at the end, with your answers filled in:

1. **`.claude/settings.json`** — syntek-author's settings allow neither the toolkit nor ffmpeg, so every toolkit call would prompt, ask for nothing before a credit-spending call, and deny no edit in media's output folders. Add the four `Bash(…)` entries to `permissions.allow`, the nine ElevenLabs entries and the two `voice remix run` entries to `permissions.ask` and the two `Edit(…)` entries to `permissions.deny`, beside the entries already there (`WebSearch` and `WebFetch` are already allowed):

   ```json
   "allow": [
     "Bash(python3 toolkit/*.py *)",
     "Bash(uv run toolkit/*.py *)",
     "Bash(ffmpeg *)",
     "Bash(ffprobe *)"
   ],
   "ask": [
     "mcp__elevenlabs__text_to_speech",
     "mcp__elevenlabs__speech_to_text",
     "mcp__elevenlabs__compose_music",
     "mcp__elevenlabs__text_to_sound_effects",
     "mcp__elevenlabs__speech_to_speech",
     "mcp__elevenlabs__voice_clone",
     "mcp__elevenlabs__isolate_audio",
     "mcp__elevenlabs__text_to_voice",
     "mcp__elevenlabs__create_voice_from_preview",
     "Bash(python3 toolkit/media.py voice remix run *)",
     "Bash(uv run toolkit/media.py voice remix run *)"
   ],
   "deny": [
     "Edit(**/generated/**)",
     "Edit(**/renders/**)"
   ]
   ```

   The ElevenLabs server marks every tool as read-only, so only an `ask` rule makes Claude Code stop before a call that spends credits. Voice remix is the one ElevenLabs call the toolkit makes itself, because the server has no remix tool; the toolkit `allow` entries would let `python3 toolkit/media.py voice remix run` spend credits unprompted, so its two `ask` entries, which take precedence over an `allow`, make Claude Code stop first. The two denies keep hand edits out of every `generated/` and `renders/` folder, whose files the toolkit and ElevenLabs write.
   The standalone seed's other entries — the eight Scrapling and code-review-graph asks, the `mcp__code-review-graph__embed_graph_tool` deny and the `hooks` block with the two handoff hooks and the data-root guard — are syntek-author's own, byte for byte. A `settings.json` that syntek-author v0.5.0 or later seeded holds them already. Any other needs them too, because `.mcp.json` and each client's file declare the Scrapling and code-review-graph servers: one syntek-author seeded before v0.5.0, or your own in a standalone project. Add these beside the entries above, and the whole `"hooks"` object of `template/.claude/settings.json` at the template's source:

   ```json
   "ask": [
     "mcp__scrapling__stealthy_fetch",
     "mcp__scrapling__bulk_stealthy_fetch",
     "mcp__scrapling__open_session",
     "mcp__scrapling__session_fetch",
     "mcp__scrapling__fetch",
     "mcp__scrapling__bulk_fetch",
     "mcp__code-review-graph__apply_refactor_tool",
     "mcp__code-review-graph__generate_wiki_tool"
   ],
   "deny": [
     "mcp__code-review-graph__embed_graph_tool"
   ]
   ```

   syntek-author's own update offers a file it seeded before v0.5.0 the asks, the deny and the two handoff hooks, but never the data-root guard: there, add the guard's `PreToolUse` entry by hand.
   Then, whether the file was skipped or not, carry the asks and denies to the other coding agents' files the project has: `python3 .claude/syntek-media-permissions.py --write` (it never creates a file, and prints what a client cannot express).

2. **Optionally**, a row in `README.md`'s layout table and the four media layers in root `CONTEXT.md`'s tree, and a line in `.claude/CLAUDE.md` naming `.claude/rules/syntek-media/`. Optional because the media rules load at launch whatever those files say.
3. **Nothing in `.gitignore` or `.mcp.json`.** Media's ignore rules are nested inside its own folders, and the ElevenLabs server is added at user scope.
4. **`git lfs install`, once**, if you will keep large design exports in `brand/src/exports/large/`. Afterwards the repository-local `filter.lfs.required` the tripwire may have set is harmless, because git-lfs sets the same value.
5. **Run `python3 toolkit/media.py check --setup`** (the workflow `brand/workflows/06-check-the-setup/`) and clear what it reports before the first credit-spending call.

## Generating a standalone project

From the published template:

```bash
uvx copier copy --trust gh:Syntek-Dev/syntek-media my-channel
```

From a local clone, rendering the checkout you have rather than the latest release tag:

```bash
uvx copier copy --trust --vcs-ref=HEAD "$(realpath ../syntek-media)" my-channel
```

The template path must be absolute, as `"$(realpath ../syntek-media)"` makes it, because Copier records it in the answers file and every later update reads the template from there; a relative path makes every update fail with 'Updating is only supported in git-tracked templates'.
A project rendered from `HEAD` must also be updated with `--vcs-ref=HEAD` (still with `-a .copier-answers.syntek-media.yml`) until a newer release tag exists, because Copier refuses to move it back to the older tag.

**The `MissingFileWarning` is expected.** On a fresh copy, and on every update, Copier may warn that `.copier-answers.syntek-media.yml` was not found. It is harmless. The template looks for your previous answers so that an update can refuse a changed `BRAND_KIND`; on a first copy there are none yet, and an update's temporary renders read the path too. Since 0.5.0, where syntek-author has never been applied, Copier also warns that `.copier-answers.syntek-author.yml` was not found, on every copy and update. That is harmless too: media reads syntek-author's answers file only for its data-root answers, so that one project keeps one store (DESIGN.md D14, D80).

**Why `--trust`.** After rendering, the template runs three small tasks, all on a copy only: `git init` (only where no repository exists); `chmod +x` on the hooks in `.claude/hooks/`, because a checkout of the template does not always carry the bit; and the Git LFS tripwire, which sets `filter.lfs.required` in the repository's own `.git/config` where no LFS filter is configured, so that a large design export cannot be committed whole by mistake. Copier treats any task as an unsafe feature and refuses to run one without `--trust`. Every task is non-fatal.

Without prompts, for scripts and CI, pass every answer that has no default and accept the rest:

```bash
uvx copier copy --trust --defaults \
  --data BRAND_KIND=author-fiction \
  --data "BRAND_NAME=Morgan Example" \
  --data "BRAND_DESCRIPTION=Trailers, read-aloud clips and the audiobook of a fantasy novel, for readers who have not yet opened the book." \
  --data 'PLATFORMS=[youtube, tiktok, instagram]' \
  --data 'MEDIA_KINDS=[trailer, short-video, audiobook]' \
  --data DATE=03/10/2026 \
  gh:Syntek-Dev/syntek-media morgan-example-media
```

`BRAND_KIND` has no default on purpose: without it, `--defaults` stops with an error rather than quietly generating a business brand.
A list takes the choice values, never their labels.

Standalone, the shared files are media's own copies, and the project works without the writing companions: there is no writing router and no project settings file, and a skill that would use a companion says which one is missing. The working-practice skills (`grilling`, `grill-me`, `grill-with-docs`, `handoff`, `to-questionnaire`, `wait-what` and `wayfinder`), the two handoff hooks in `.claude/hooks/` and the `handoffs/` folder ship with media as they do with syntek-author, byte for byte the same (D80).
When generation finishes, open the project in Claude Code. The generated `README.md` and `CONTEXT.md` describe that project; `.claude/CLAUDE.md` holds its brief and points at the rules.

## What `copier update` will and will not touch

Every file in a generated project belongs to one of five classes. Knowing which is which is the whole of updating safely.

**1. Template files — updated, and merged with your edits.**
The rules in `.claude/rules/syntek-media/`, media's own skills and the `MEDIA-<KIND>.md` mode files it adds to five of the working-practice skills, the bridge, data-root and permissions files in `.claude/` (`syntek-media-agents.md`, `syntek-media-dataroot.py`, `syntek-media-dataroot.json` and `syntek-media-permissions.py`), every folder's `CONTEXT.md` and `CLAUDE.md` (apart from the seeded and shared ones below), the reference guides in `docs/reference/`, the numbered workflows, the toolkit with its platform data and fallback layouts, every nested `.gitignore` and `.gitattributes`, and the `README.md` of every `generated/`, `renders/` and `raw/` folder.
An update brings the template's improvements and keeps your local edits through a three-way merge; where both changed the same lines you get a conflict to resolve.
Better than editing them: put your own guide in `docs/project/` (a guide there with the same name overrides the reference guide, though it may only add checks to a gate of the piece ladder, never remove one), your own procedure in `workflows/local/` (a local workflow with the same name overrides the template's), a confirmed change to a platform's limits as an `[[override]]` row in `brand/src/platforms/overrides.toml`, and your own rules where syntek-author's project settings file says, or in `.claude/CLAUDE.md` under 'Project-specific rules' in a standalone project.

**2. Seeds — written once if missing, then yours.**
The design register, `tokens.css` and the seven preview cards in `brand/src/design-system/` (among them `thumbnail.html` and `card.html`, the brand's own layouts), `voice.md`, `overrides.toml` and one profile per platform in `brand/src/platforms/`, the piece register, the rights register, the credits log, the footage manifest, the schedule, the publish log, and the `CONTEXT.md` and `CLAUDE.md` of every `docs/project/` and `workflows/local/` (you add a row to them).
An update never overwrites one that exists. If you delete one, the next update puts a fresh, empty copy back, because skills and rules read it by path.
The cost: once a seed exists it never receives the template's improvements. A release that must change a seed ships a migration that edits your copy only where exactly one change is correct.
**The one exception: removing a platform or a media kind deletes every file it generated, seeds included**, even a platform profile you have filled in (see [Updating a project](#updating-a-project)).

**3. Shared files — written once by a copy, and never touched again.**
`README.md`, `CONTEXT.md`, `.gitignore`, `.mcp.json`, `.claude/CLAUDE.md`, `.claude/CONTEXT.md`, `.claude/MEMORY.md`, `.claude/settings.json` and the `CONTEXT.md` and `CLAUDE.md` of `.claude/skills/`, plus `AGENTS.md`, `GEMINI.md`, `.agents`, `.codex/config.toml`, `.codex/CONTEXT.md`, `.codex/CLAUDE.md`, `.claude/mcp_config.json`, `.agents/skills` and `.agents/mcp_config.json` (D73, D76).
Since 0.4.2 `.agents` is the real folder that holds the last two, and `.claude/mcp_config.json` is no longer written by a copy: Antigravity reads `.agents/mcp_config.json`. A project that already has it keeps it.
Since 0.5.0 (D80) also `.gemini/settings.json`, `.gemini/CONTEXT.md`, `.gemini/CLAUDE.md` and `opencode.json`; the `SKILL.md` of the seven working-practice skills (`grill-me`, `grill-with-docs`, `grilling`, `handoff`, `to-questionnaire`, `wait-what` and `wayfinder`); `.claude/hooks/pre-compact-handoff.sh`, `.claude/hooks/context-threshold-handoff.sh` and the `CONTEXT.md` and `CLAUDE.md` of `.claude/hooks/`; and those of `handoffs/`. These are syntek-author's family-shared files, byte for byte the same in both templates. A coding agent's files are written only for the clients ticked in `AGENT_CLIENTS`.
A copy writes one only where it does not already exist. An update never renders it at all, so your edits are never merged into, and one you delete stays deleted.
Existing shared paths remain the author's; media fills only missing paths. In a standalone project they are media's initial copies, and yours to edit.

**4. Examples — copied once, and they stay deleted.**
The worked example piece `000-example-piece`, with its edit decision list, title card, cut-down plan, captions, thumbnail and post package. They arrive on the first `copier copy` (unless `SEED_EXAMPLES` is false) and an update never renders them again: delete them when you are done and they never come back; keep and edit them and an update leaves them alone.
The example is a plan, walked through to `storyboarded`: it names footage no project has, so `media.py assemble` on it stops for want of that footage, as it should.

**5. Your folders — the template ships only the signposts.**
`scripts/src/pieces/` (each piece folder then carries its own pair), `production/src/footage/`, `assets/`, `edits/`, `cards/`, `voiceover/`, `timing/`, `scenes/` and `audiobook/`, `publishing/src/cut-downs/`, `captions/`, `thumbnails/` and `posts/`, `brand/src/design-system/fonts/`, `brand/src/exports/` and `exports/large/`, `brand/src/voice/` and `brand/src/platforms/`, and every `docs/project/` and `workflows/local/`.
The template ships each folder's `CONTEXT.md` and `CLAUDE.md` (and any seed or ignore file named above) and nothing else, so nothing you put there is ever touched.

Your scripts, transcripts, footage, takes, renders and published copy are never template files.

## Updating a project

Always on a branch, always with the answers file named, and with Git's automatic housekeeping off for the run:

```bash
git switch -c update-syntek-media
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx copier update --trust -a .copier-answers.syntek-media.yml
git status && git diff     # review; resolve any conflict markers
git add -A && git commit -m 'Update from syntek-media'
```

**Why housekeeping off.** Copier renders the template into temporary Git repositories and commits in them, and after a commit Git may start its automatic maintenance in the background. If that is still writing when Copier deletes the temporary folder, the update stops with `OSError: [Errno 39] Directory not empty` on a `.git/objects` path under a `copier._main.old_copy.…` or `copier._main.new_copy.…` folder. It is intermittent, most likely with Git 2.54 or 2.55 (Git 2.56 starts the background repack only above about 7,000 loose objects) and with several updates running at once. The five variables in front of the command turn `gc.auto` and `maintenance.auto` off for that one command, in every Git it starts, and change none of your Git settings. The form is for POSIX shells such as bash and zsh, and needs Git 2.31 or later. Give every other update command in this README the same five variables in front.

**If an update stopped with that error,** Copier had already written the new version's files and recorded the new version in `.copier-answers.syntek-media.yml`, but nothing that runs after the render had run: no after-stage migration (the release's own report, such as 0.4.2's, included), and an `.agents` link outside the project is still held aside. Never commit that state: an update run over it takes the new version as already reached, so it reports 'Keeping template version 0.4.5' and skips that release's migrations. Discard it and run the update again, from the project root, in this order. First, if `.agents.syntek-held` exists, put the link back as 'Migrations' below says: `git clean -fd` would delete it. Next run `git clean -n -d`, a dry run that deletes nothing: it lists every untracked file and folder the discard would delete, not only the update's (Copier refuses to start over untracked files only where Git shows them: with `status.showUntrackedFiles` set to `no`, it runs over yours), so commit or move out of the project anything of yours it lists; files Git ignores are left alone. `git reset --hard` discards every uncommitted change in the repository, so the project must be its own repository. Then:

```bash
git reset --hard && git clean -fd
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx copier update --trust -a .copier-answers.syntek-media.yml
```

The second run updates from the version you had (Copier prints 'Updating to template version 0.4.5', say, not 'Keeping template version 0.4.5'), runs every migration the crossing calls for, and delivers what an update that never stopped delivers.

**Why `-a`.** The answers file is called `.copier-answers.syntek-media.yml`, not Copier's default `.copier-answers.yml`, so that it can sit beside syntek-author's own. Copier only finds a non-default answers file when you name it; without `-a` it stops and changes nothing.

**Changing an answer.** Pass it on the update. A list answer replaces the whole list, so pass every value you want, for example adding TikTok:

```bash
uvx copier update --trust -a .copier-answers.syntek-media.yml \
  --data 'PLATFORMS=[youtube, tiktok, instagram, linkedin]'
```

**Removing a platform or a media kind deletes what it generated.** A value you leave out of the list loses every file it generated, seeds included, even a platform profile you have filled in — they survive only in your git history — and every file you created yourself stays: your chapter registers in `production/src/audiobook/`, your pieces, your footage.
Copy out and commit anything you need first. Every update prints, before it asks its questions, what removing each platform and each media kind deletes, workflows by full folder name.
After a change, edit by hand the files that describe your options, because an update never rewrites them: in a standalone project `README.md`, `CONTEXT.md` and `.claude/CLAUDE.md` Section 1 (over syntek-author they are syntek-author's), and any rows for a removed platform in `brand/src/platforms/overrides.toml`. The brand section of the media rules, `.claude/rules/syntek-media/01-layout-and-routing.md` Section 1, updates itself.

`BRAND_KIND` cannot change: an update that answers it differently stops before touching a file, because the mode files, the worked example and the brand seeds were written for one kind of brand. A different brand kind is a new project.

The `MissingFileWarning` about `.copier-answers.syntek-media.yml` appears on every update and is harmless, as does a second one about `.copier-answers.syntek-author.yml` in a project syntek-author has never been applied to (since 0.5.0: media reads that file only for syntek-author's data-root answers).
A project rendered from a local clone at `HEAD` (see [Generating a standalone project](#generating-a-standalone-project)) updates with `--vcs-ref=HEAD` added to the command above, until a newer release tag exists.

**Migrations.** When a release moves a folder that can hold your work, or stops shipping a seed, the update runs a migration script from the template after it has written the new tree; it moves or keeps your files only where exactly one outcome is right, and never overwrites or deletes one.
The first is 0.4.2's (D76). Earlier releases shipped `.agents` as a link to `.claude`, which makes every sandboxed Codex command fail, and an update never touches a shared path. So, only where `.agents` is a link whose target is exactly `.claude`, the migration removes that link (never `.claude`), creates the real `.agents/` folder, links `.agents/skills` to `../.claude/skills`, and moves `.claude/mcp_config.json` to `.agents/mcp_config.json` where that path is free. A real folder, a link elsewhere, a text file Git checked out in place of the link, or no `.agents` is left untouched and reported, as is every tracked line that still describes the old layout. It is the first of the two changes media ever makes to a shared path. Review its report and commit; it prints the command that runs it again.
The second runs on every update and is keyed to no release (D76). Copier refuses to render anything beneath an `.agents` link that leaves the project, so where `.agents` is such a link, the update renames it to `.agents.syntek-held` before the render and back afterwards: the net change is zero, and its target is never touched. If an update stops before it ends (a refused answer, Ctrl-C at a question, or Copier failing as it cleans up after the render), the link stays held as `.agents.syntek-held`, and the next update refuses the changed tree; where the link is committed and the update stopped after its render, Copier has already put an identical `.agents` link back. Put the link back from the project root, in a POSIX shell (Terminal on macOS and Linux, Git Bash on Windows; never PowerShell's `rm`), before anything else, and before discarding the stopped update with `git reset --hard` and `git clean -fd`, which would delete a held link Git does not track. First check what stands at `.agents`: `ls -ld .agents .agents.syntek-held`. Where it shows no `.agents.syntek-held`, nothing is held: stop here and change nothing. Where `.agents` is a link (its line shows `->`), remove that link alone with `rm .agents` (never `rm -r`, never a trailing slash); where it is a folder or a file, move it aside to a name nothing holds yet (`ls -ld .agents.from-update` finds nothing) with `mv .agents .agents.from-update` (no trailing slash), which holds what the update wrote (check it, and delete nothing in it that is yours). Then, once `ls -ld .agents` finds nothing, run `mv .agents.syntek-held .agents` (no trailing slash). Never run that `mv` while `.agents` stands: it would put the held link inside it, and inside the folder outside the project where `.agents` is a link. Then update again; where `git status` still shows changes (a stop after the render), discard the stopped update first: run `git clean -n -d`, a dry run, move out of the project anything of yours it lists, then `git reset --hard && git clean -fd`. Where the held link was committed beside an identical `.agents` link, the next update moves nothing, says so, and asks you to remove the held link (`rm .agents.syntek-held`), commit, and update again. `copier update --pretend` still refuses such a project, because a pretend run skips migrations.

**Settings an update cannot add.** `.claude/settings.json` is a shared file, so no update changes it. Release 0.4.4 added two `ask` entries for `voice remix run` ([the hand edits](#the-hand-edits-after-a-copy)); a project made before it adds them by hand, and until then `python3 toolkit/media.py check --setup` reports each missing one as a FAIL with the line to add. Seeds never update either: the same release changed the Consent rule of `brand/src/voice/voice.md` (a remixed voice cites its source clone's consent ID) and the rules of `production/src/credits-log.md` (the `voice remix` row), which an older project edits by hand.

**Known limitation: what an update to 0.5.0 does not bring, until 0.6.0.** Release 0.5.0 adds files media shares with syntek-author (D80): the seven working-practice skills, the two handoff hooks with the `CONTEXT.md` and `CLAUDE.md` of `.claude/hooks/` and of `handoffs/`, the Gemini CLI and OpenCode files, two MCP servers in `.mcp.json` and each client's file, and new entries in the settings seed (the Scrapling and code-review-graph asks, the `embed_graph_tool` deny, and a `hooks` block with the two handoff hooks and the data-root guard). Each is a shared file, which an update never renders: a copy made with 0.5.0 has them, and an update from an older release delivers none of them. The update script that adds and refreshes them is syntek-author's, and media takes it in 0.6.0 (D81).
Over syntek-author, syntek-author's own update keeps the shared skills and hooks current, and offers the settings entries, all but one: it never adds the data-root guard (the `PreToolUse` entry of the seed's `"hooks"` object) to a `settings.json` it seeded before v0.5.0, so add that entry by hand from `template/.claude/settings.json` at the template's source.
In a standalone project the update brings only media's own files: the data-root and permissions scripts and the `MEDIA-<KIND>.md` mode files, which land in skill folders that still lack their `SKILL.md` (a skill folder without one is inert), and it leaves empty `.claude/hooks/`, `handoffs/`, `.claude/skills/grill-me/` and `.claude/skills/wait-what/` folders, which Git does not track.
To add the missing files by hand, render the release you now have into a temporary folder from your own answers, then copy across only what you lack, from the project root:

```bash
T="$(mktemp -d)/media"
uvx copier copy --trust --defaults --vcs-ref=v0.5.0 --data-file .copier-answers.syntek-media.yml \
  gh:Syntek-Dev/syntek-media "$T"
for f in .claude/hooks/CONTEXT.md .claude/hooks/CLAUDE.md .claude/hooks/pre-compact-handoff.sh \
    .claude/hooks/context-threshold-handoff.sh handoffs/CONTEXT.md handoffs/CLAUDE.md \
    .claude/skills/{grill-me,grill-with-docs,grilling,handoff,to-questionnaire,wait-what,wayfinder}/SKILL.md; do
  [ -e "$f" ] || { mkdir -p "$(dirname "$f")" && cp -p "$T/$f" "$f"; }
done
git status
```

The loop never replaces a file you have. Then add by hand to `.claude/settings.json` what `"$T/.claude/settings.json"` holds and yours lacks: the eight `mcp__scrapling__…` and `mcp__code-review-graph__…` entries under `"ask"`, `mcp__code-review-graph__embed_graph_tool` under `"deny"`, and the whole `"hooks"` block. Compare `.mcp.json` with the temporary copy's and take its two servers if you want them; with the code-review-graph server, also add the line `/.code-review-graph/` to your `.gitignore`, as `"$T/.gitignore"` has it, so that Git ignores the graph's database. A coding agent's files come from the bridge's steps, `.claude/syntek-media-agents.md`, after you record the client with `--data "AGENT_CLIENTS=[...]"` on an update. Use the release your answers file records as `_commit` in place of `v0.5.0` when you are on a later one, and the template's local path with `--vcs-ref=HEAD` where you update from a clone.

Commit `.copier-answers.syntek-media.yml` and never edit it by hand; it is the record every future update merges against.

## Living beside syntek-author

syntek-author was built to share a repository with a second template, and syntek-media is that template. Five rules make sharing safe, and media keeps each:

1. Each template records its answers in its own file — this one's is `.copier-answers.syntek-media.yml`.
2. Each template keeps its instructions in its own folder, `.claude/rules/<template>/`. No template updates `.claude/CLAUDE.md`, which stays yours. Media's eight rules files load at launch beside syntek-author's, and the brand brief lives in the first of them, so it updates with the answers.
3. The shared files are written by whichever template comes first and updated by none. Media is stricter than a seed: its thirty-six shared paths are copy-only, so an update never recreates one you deleted. Seventeen of them, new in 0.5.0, are syntek-author's family-shared files — the working-practice skills, the two handoff hooks and the `.claude/hooks/` and `handoffs/` pairs, and the Gemini CLI and OpenCode files — which both templates ship byte for byte the same, so a combined project holds one copy whichever came first (D80). Its own ignore rules live in nested `.gitignore` files inside its own folders.
4. Skill and layer names never collide. The writing skills ship only from syntek-author; the seven working-practice skills ship from both, byte for byte, and media's own mode files beside five of them are named `MEDIA-<KIND>.md`, so they never meet syntek-author's. The names media must never take are frozen in `.github/scripts/syntek-author-names.txt`, which two audits read on every run.
5. Large binaries never sit in plain Git: renders and generated audio are ignored, footage and approved takes live in external storage, and Git LFS holds only large design exports.

Apply each template with its own answers file and update each separately. Copier refuses to update a repository with uncommitted changes, so each command starts from a clean, committed tree:

```bash
uvx copier copy --trust gh:Syntek-Dev/syntek-media .
git add -A && git commit -m 'Apply syntek-media'
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx copier update --trust -a .copier-answers.syntek-author.yml
git add -A && git commit -m 'Update from syntek-author'
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx copier update --trust -a .copier-answers.syntek-media.yml
git add -A && git commit -m 'Update from syntek-media'
```

The other order works too — media first, then syntek-author, both without `--overwrite` — but choose syntek-author first where you can. Whichever template comes first writes the shared files, and media's leave out what syntek-author needs. syntek-author prints no message after its copy, so in the media-first order add these by hand from syntek-author's own template files, then commit:

- **`.claude/settings.json`:** its allows `Bash(make *)` and `Bash(python3 tooling/*.py *)`, plus `Bash(sqlite3 tooling/references.db *)` or `Bash(uv run tooling/font.py *)` where its references or constructed-language options are on; and its denies `Edit(**/*.pdf)` and `Edit(build/**)`, plus `Edit(typeset/src/units/.base/**)` outside a business project. Keep media's own entries. Since 0.5.0 media's seed already carries syntek-author's `hooks` block (the two handoff hooks and the data-root guard), its Scrapling and code-review-graph asks and its `embed_graph_tool` deny, byte for byte.
- **`.gitignore`:** the sections media's copy does not carry: its build output (`/build/`); its SQLite sidecars (`*.db-journal`, `*.db-wal`, `*.db-shm`); its Word and LibreOffice lock files (`.~lock.*#`, `~$*.docx`, `~$*.xlsx`, `~$*.pptx`); and its TeX intermediates (`*.aux`, `*.log`, `*.out`, `*.toc`, `*.fls`, `*.fdb_latexmk`, `*.synctex.gz`, `*.xdv`). Check with `git check-ignore build/x.pdf`.
- **`README.md`, `CONTEXT.md`, `.claude/CLAUDE.md` and `.claude/CONTEXT.md`** describe media only. Optionally add syntek-author's layers and its rules folder, `.claude/rules/syntek-author/`: its rules load at launch whatever these files say, and media's `.claude/CLAUDE.md` already defers to its project settings file.

In a combined project:

- **syntek-author's project settings file outranks media's rules.** Where `.claude/rules/syntek-author/00-project.md` is present, media reads it at run time, never through Copier: its Paths say where project rules and handoffs go, its Memory headings map the headings of `.claude/MEMORY.md`, a Workflow aliases row may name a media workflow by its full folder path, and an Overrides row may name a media rules file and section.
- **Two routers, two kinds of work.** syntek-author's router never sees media's layers. Media's own, `run-media-workflow`, routes video, audio, captions, thumbnails and posting, and leaves writing work to syntek-author's router, where present.
- **The social-media family owns the written social plan.** In a business project with syntek-author's social-media family (on by default), its documents own the social media plan, the content calendar, the bios, the channel voice and text-only posts. Media's platform profile then holds only delivery facts, its schedule lists only media deliverables, each citing its calendar entry, and its post packages cite the entry too.
- **The writing skills are companions.** Media runs spelling, grammar, comprehension, flow and fact-check on scripts, transcripts and post copy as reports, and improve-section and adapt-section on a script only as a report followed by the edits you agree, with no ledger entry: the provenance ledger belongs to syntek-author's content layer.
- **The skills signposts are syntek-author's.** `.claude/skills/CONTEXT.md` lists syntek-author's roster and calls any other skill your own; media's skills are listed in `.claude/rules/syntek-media/02-skills.md` and are template-owned by syntek-media.
- **`make flags` and `make lint` read media's `src/` Markdown too**, so media's scripts, registers and plans are written one sentence per line.
- **syntek-author's own audits run on a syntek-author-only render.** Its `doc-references.sh` stays clean on a combined tree, but its `skill-conformance.sh`, `shipped-variants.sh` and `docs-pairing.sh` flag media by design: media's skills are outside its catalogue, a mode file sits on a skill it treats as unmoded, and its `docs-pairing.sh` does not know media's `generated/`, `renders/` and `raw/` folders, which carry only a `README.md`.
- **Hand off, never compact.** The handoff skill and its two hooks ship with both templates, byte for byte (D80); the handoff goes in the folder syntek-author's Paths give, or in `handoffs/` in a standalone project.

## Large files: renders, audio and footage

Big binaries never sit in plain Git. Each kind of large file has one home:

- **Renders and generated audio are ignored.** Every `renders/` and `generated/` folder keeps only its `README.md` in Git; masters, cuts, card and thumbnail PNGs, takes and audiobook chunks are ignored by nested `.gitignore` files that ship in every project, whatever platforms and media kinds you chose. Each piece's output sits in a folder named for it inside `production/src/renders/`, `production/src/voiceover/generated/` (its takes in `takes/`) and `publishing/src/renders/`, ignored whole; a piece's tracked timing and scene files stay flat, under its name, in `production/src/timing/` and `production/src/scenes/`. A render is regenerable from tracked files.
- **Source footage lives in external storage, by decision.** Every recorded or licensed source file — camera footage, recorded audio, music beds, stock — has a row in `production/src/footage/manifest.toml` (path, sha256, size, duration, and a label for where the master copy lives), and a local mirror in the ignored `production/src/footage/raw/`. `python3 toolkit/media.py footage add` copies a file into the mirror (it never moves one) and hashes it; `footage verify` proves the mirror matches the manifest. Footage is large and rarely diffed, it would exhaust LFS storage and bandwidth quotas, and the checksums keep every edit reproducible.
- **Approved generated audio is archived the same way.** A take cannot be made again — regenerating it spends credits and gives a different take — so an approved take or mastered chapter is logged with `footage add --kind generated` before the piece is produced. For an audiobook the approved mastered chapter is what must be kept; its chunk takes may be, on your word.
- **Git LFS holds only large design exports**, in `brand/src/exports/large/`, through a nested `.gitattributes` that exempts itself and the folder's pair. Small exports are committed in `brand/src/exports/`. Never add a root `.gitattributes` and never run `git lfs track`, which writes one: it would be a shared root file neither template seeds.
- **Two guards.** Without a configured LFS filter, git commits an LFS-marked file whole, silently. The copy's tripwire sets `filter.lfs.required` where no filter is configured, so that `git add` fails loudly instead, and `python3 toolkit/media.py check` reports LFS-marked files stored as plain blobs, LFS-marked files with no filter configured, and any file over 10 MB outside the ignored and LFS folders.
- **The data root files nothing of media's yet.** The family can keep a project's binaries outside the repository, under each machine's data root (`DATA_STORE` external; see [The questions](#the-questions)). Media's map, `.claude/syntek-media-dataroot.json`, names no folder in 0.5.0 (D80), so footage, takes and exports stay as above whatever the answer. Its resolver, `python3 .claude/syntek-media-dataroot.py root`, reports the root and the answers, and the data-root guard in the settings seed keeps the session's file tools out of the root. Where media's answers and syntek-author's differ, the update says so, and the data commands refuse until they agree.

## Audio with ElevenLabs

The voiceover, narration and captions skills generate audio and transcripts through an ElevenLabs MCP server named `elevenlabs`. They only call it when you ask; before any call they state the characters or audio minutes, the number of calls and the estimated credits, and wait for your yes; they make one call at a time; and every spend gets a row in `production/src/credits-log.md`.

The template adds **no ElevenLabs server** to the project's `.mcp.json`, which holds only Scrapling and code-review-graph. Add the server once, at **user** scope, so it is available to every project on your machine and its key lives in your own Claude Code configuration (`~/.claude.json`), never in a repository.
**Its base path must contain the project.** The server saves every file under `ELEVENLABS_MCP_BASE_PATH` (default `~/Desktop`) unless a skill passes an absolute folder, which media's skills always do, and it refuses to read any input file outside that path — so with the default, speech-to-text rejects every project file with 'outside of allowed directory'. The path is resolved before the test, so a symbolic link does not help.
Use `$HOME` when every project lives under it; otherwise the nearest folder that holds them all, such as the disk your repositories live on. An existing server, syntek-author's included, is removed and added again:

```bash
claude mcp remove elevenlabs --scope user
claude mcp add --env ELEVENLABS_API_KEY="$ELEVENLABS_API_KEY" --env ELEVENLABS_MCP_BASE_PATH="$HOME" \
  --transport stdio --scope user elevenlabs -- uvx elevenlabs-mcp
```

Replace `"$HOME"` with that folder where your projects live elsewhere; when the error appears, the `captions` skill prints the exact command with a base path it has computed to contain the project.
Export the key in your shell first rather than typing it on the command line, and never commit it. The server must be named `elevenlabs`: the skills call its tools by that name (`mcp__elevenlabs__text_to_speech`).

- **Permissions.** The server marks every tool read-only, so a project's `.claude/settings.json` asks before each of the nine tools that spend credits and before `voice remix run`; over syntek-author, add those `ask` entries by hand ([the hand edits](#the-hand-edits-after-a-copy)). `python3 .claude/syntek-media-permissions.py --write` then carries them to Gemini CLI's and OpenCode's files (see [Using other coding agents](#using-other-coding-agents)).
- **Character voices.** The workflow `production/workflows/11-design-character-voices/`, in every brand kind, designs a character's voice from your own cloned voice: it drafts a description from the manuscript or script, `python3 toolkit/media.py voice remix plan` shows the one call first, and `voice remix run --approve-call` sends it straight to ElevenLabs with the `ELEVENLABS_API_KEY` exported in your shell, saving the previews as a voice trial. You listen and choose; the chosen preview is saved through the server (`mcp__elevenlabs__create_voice_from_preview`) and recorded in `brand/src/voice/voice.md` under the consent of the voice it came from. Remix accepts only a voice your account created, never a Voice Library voice. One voice per take for now: a piece that switches voice between segments is not supported yet.
- **The model** is discovered with `mcp__elevenlabs__list_models` and recorded per use in `brand/src/voice/voice.md`, never assumed.
- **Voiceover** is made one segment per spoken sentence or beat, so the captions can be timed from the segments' own durations at no cost.
- **Output formats.** The skill chooses the format for the deliverable and says when it needs a higher ElevenLabs plan: `mp3_44100_192` needs Creator or above, and `pcm_44100` Pro or above.
- **Audiobooks** have no script: the chapter register, with its opening and closing credits, is the plan you approve first. They have three routes, chosen per channel with you. ACX and Audible need a human narrator unless you are authorised otherwise; an AI master through the server goes only to channels that accept one; and a channel that takes only ElevenLabs' own package is made in ElevenLabs' studio, outside this template.
- **Disclosure.** Every piece with a synthetic voice — your own cloned voice included — records it in its brief. At publish, each platform's AI label is set exactly when that platform's rule requires it, and a disclosure line goes in every description.
- **Without the server**, `espeak-ng`, where installed, makes a scratch track for timing, labelled approximate.

## Design with Claude Design

Visual design happens in Claude Design, in one design-system project per brand.
The repository holds the source of truth: `brand/src/design-system/tokens.css` (the CSS custom properties every layout imports), the brand's fonts, and preview cards whose first line, `<!-- @dsCard group="…" -->`, files each card in the Design System pane.
Two of those cards are the brand's own layouts — `previews/thumbnail.html` and `previews/card.html` — which every new piece's thumbnail and title card is copied from, so a layout changed in Claude Design and synced reaches every later piece.
You start the sync, with `/design-sync`, and it works one component at a time, never a wholesale replace (the workflow `brand/workflows/02-sync-with-claude-design/`). Its converter expects a React kit, so the first sync of this plain HTML kit is checked by hand; `/design import` and `/design export` are the fallback route.
Each exported design is recorded in `brand/src/design-register.md` with its Claude Design link and where the export is kept. There is no design editor, no React and no Node in the project.

## Using other coding agents

Claude Code's `.claude/` tree is canonical and always ships. A copy also writes the files of the coding agents ticked in `AGENT_CLIENTS` (all four on a fresh copy), each only where it does not already exist (D80, syntek-author D47):

| Client      | Its files                                                                 |
| ----------- | ------------------------------------------------------------------------- |
| Codex       | `AGENTS.md`, `.codex/config.toml` and the `.codex/` pair                  |
| Gemini CLI  | `GEMINI.md`, `.gemini/settings.json` and the `.gemini/` pair              |
| Antigravity | `GEMINI.md` and `.agents/mcp_config.json`                                 |
| OpenCode    | `AGENTS.md` and `opencode.json`                                           |

Any of them also gets a real `.agents/` folder holding the relative link `skills -> ../.claude/skills`. `.agents` is never itself a link: Codex mounts it read-only, and its sandbox refuses a read-only link to a writable folder (D76). These files are syntek-author's, byte for byte, so a combined project receives the same ones whichever template comes first. Every client reads the template-owned `.claude/syntek-media-agents.md`, and every other `.claude/syntek-*-agents.md` present, which route to the canonical rules, project memory, folder pairs, skills and mode files. Local and project-specific rules still win.

A model you name in `CODEX_MODEL`, `GEMINI_MODEL` or the `OPENCODE_*` answers is written into that client's file by the copy, and the tier it serves is a row in the model table of `.claude/rules/syntek-media/05-model-allocation.md`; change the client's file by hand later. Codex's `.codex/config.toml` enables `CLAUDE.md` as a fallback instruction filename once the project is trusted, and sets no trust level, permission bypass or credentials. The Opus and Sonnet labels in workflows identify work tiers on other clients; a capability unavailable in a client needs the documented manual route.

**MCP servers.** `.mcp.json` and each client's own file carry two servers, pinned and keyless: `scrapling` (web pages) and `code-review-graph` (a local map of the code). The ElevenLabs server is never among them: it is added at user scope (see [Audio with ElevenLabs](#audio-with-elevenlabs)). Use them as `.claude/rules/syntek-media/06-global-rules.md` Section 13 says: ask before each of Scrapling's six browser tools, and never run `code-review-graph install` or `scrapling install`. Codex and Gemini CLI start them only in a trusted project; OpenCode starts them when it opens the project and runs every tool the project does not ask for without a prompt. The first start downloads them through `uvx`.

**Permissions in every client.** `.claude/settings.json` holds the project's ask and deny rules, the ElevenLabs asks among them. After a copy, and whenever you change those rules, carry them to the other clients' files that exist:

```bash
python3 .claude/syntek-media-permissions.py --check    # what is missing, and what a client cannot express
python3 .claude/syntek-media-permissions.py --write    # adds the missing rules; never creates a file
```

It never writes an allow rule, never removes or reorders one, and prints what to set by hand where a client cannot express a rule (Antigravity's settings are set in the app).

**Existing projects:** an update never adds, changes or recreates a client's files. Record the clients you use with `--data "AGENT_CLIENTS=[...]"` on an update, then follow the bridge's explicit setup: generate a separate temporary project using the recorded source, ref and answers, review its client files, and copy only missing files. Preserve existing instructions and settings; agree a pointer to the bridge in an existing entrypoint. Updating across 0.4.2 replaces an `.agents -> .claude` link with the real folder; preserve any real `.agents` directory or differently targeted link and resolve its integration manually. An `.agents` link to a folder outside the project is held aside and restored by every update; a copy over one needs the hand recipe at the top of this guide. On Windows, Git may check `.agents/skills` out as a text file (`core.symlinks=false`); the bridge says how to recreate the link. Never re-run a template copy with overwrite on the real project.

The template development repository has separate root entrypoints and a Codex config that
disables every product skill. Its `.agents/` is a real folder holding only its pair; it exposes no skill.

## Working on the template

Read [`DESIGN.md`](DESIGN.md) first: it is the build contract, and where any other file disagrees with it, `DESIGN.md` wins. [`CONTEXT.md`](CONTEXT.md) maps this repository, and `.claude/CLAUDE.md` is the development manual — token discipline, how to add a skill, a mode file, a gated path, a platform or a media kind, and what to run before committing. Changes are recorded in [`CHANGELOG.md`](CHANGELOG.md). To propose a change, start with [`CONTRIBUTING.md`](CONTRIBUTING.md); report a vulnerability only as [`SECURITY.md`](SECURITY.md) says.

Scene pieces use `production/docs/reference/scenes-as-code.md` and
`production/workflows/10-animate-a-scene/`: review first/middle board stills with
`uv run toolkit/scene.py stills`, then render each aspect natively with `scene.py render`.
The kit computes every frame in Python; Playwright draws only local brand art and indexed
captures. `--memory-max SIZE` or user-scope `MEDIA_MEMORY_MAX` optionally caps assemble and
scene renders under systemd with swap disabled; other runs report that they are uncapped.
No scene command calls a generation API.

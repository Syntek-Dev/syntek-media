# CONTEXT.md — migrations/

The scripts `copier update` runs when a project crosses a release that moved something an author, or a shared path, holds.
Copier only tracks what it generated: a renamed folder takes its governance pair to the new place and leaves the author's work behind, and a copy-only shared path (D11) is never rendered by an update, so a release that must change one can reach it only here.
Since 0.6.0 the vendored update script, run last on every update, refreshes the family files its data lists, offers the listed settings entries and MCP servers once each, and puts the read-only guide back: D11's third exception (D81, D84).
A migration acts where exactly one result is correct and reports everything else; a report-only one, such as `v0.6.0-how-to.py`, moves nothing and says what the release leaves to the owner.
Nothing here ships: `_subdirectory: template` keeps this folder out of every generated project, and `copier.yml` runs each script from the template clone through `_copier_conf.src_path`.

```text
├── v0.4.2-agents-folder.py     ← .agents -> .claude link → real .agents/ folder (D76)
└── v0.6.0-how-to.py            ← every brand kind, report only: where the guide starts, how-to that is not a folder, files of yours there (D84)
```

## What's here

- `agents-outside-link.py` — **every brand kind, every update; one of the two scripts not keyed to a release.** Copier refuses any destination that resolves outside the project before it reads `_exclude` (Copier 9.17.1), so where `.agents` is a link to a folder outside the project, the files under `.agents/` stop every update. Two unversioned entries, first in `_migrations` and between syntek-author's `# BEGIN`/`# END family-shared migrations (D48)` markers, run it with `_copier_python`, the interpreter running Copier: `hold` at `_stage == 'before'` renames only such a link to `.agents.syntek-held` and prints the hand fix ('By hand' below) before the render, and where the held name already stands beside `.agents` moves nothing and says what to do; `restore` at `_stage == 'after'`, declared before the v0.4.2 entry, renames it back where `.agents` is absent, removes the held link where an identical `.agents` link already stands, and otherwise moves nothing and prints the hand fix for what stands at `.agents`. A stage that fails moves nothing more, and prints the hand fix where a link is held and otherwise says that nothing is held; no stage, or an unknown one, prints its usage line. Net change zero; the link's target is never touched; standard library only; each stage always exits `0` (`--self-test` exits `1` when a probe fails). `--self-test` runs both stages and the printed fix in temporary folders, and `--help` prints its docstring. It comes from syntek-author's `v0.9.1` tag (byte for byte its `v0.6.0`'s) and, since 0.6.0, needs Python 3.14 or later (D85 as D81 amends it): below it each stage moves nothing and exits `0`, and the hold stage, and the restore stage where a link is held as `.agents.syntek-held`, first print on stderr a message framed in lines of `=` naming the Python it found and the rerun with `uvx --python '>=3.14' copier update`, so an update over an outside link then stops with `ForbiddenPathError`. It is family-shared (syntek-author D48): media vendors it and its `_migrations` block byte for byte from a syntek-author release tag, first its `v0.5.0` (D85), since 0.6.0 its `v0.8.0` (D81), now its `v0.9.1`, so it names no template and no decision number, and neither is ever edited here (`shipped-seeds.sh` checks 21 and 22 pin both). D11's second, transient exception. An update that stops between the stages leaves the link held, and the next update refuses the changed tree until the link is put back by hand. A copy runs no migration: its hand recipe is in the bridge and `README.md`.
- `v0.4.2-agents-folder.py` — **every brand kind.** Releases 0.3.0 to 0.4.1 shipped `.agents` as a link to `.claude`, which makes every sandboxed Codex command fail (D76). Only where `.agents` is a symbolic link whose target is exactly `.claude` or `.claude/`, it builds the folder beside the link, swaps it in, links `.agents/skills -> ../.claude/skills`, and moves `.claude/mcp_config.json` to `.agents/mcp_config.json` where that path is free. Everything else is left and reported, with every tracked line that still describes the old layout. Standard-library Python 3, idempotent, never deletes author content, always exits `0`; `--help` prints its header. D11's first stated exception: media changes a shared path only here, transiently through `agents-outside-link.py`, and, since 0.6.0, through `family-update.py`.
- `v0.6.0-how-to.py` — **every brand kind; report only** (D84, on the model of syntek-author's `v0.6.0-how-to.sh`, its D44 and D56). 0.6.0 adds the user guide, `how-to/`, read-only: the update writes media's own guide files by Copier's merge and the shared ones, the deny and the guard through `family-update.py`, and moves nothing. Its `version: v0.6.0` entry sits after `v0.4.2`'s and before the family 'update' block and runs through `_copier_python`, so it runs once per project, on the update that crosses 0.6.0. It parses and exits `0` on Python 3.10, the oldest Copier 9.12.0 supports; standard library only; it writes nothing, reads only the files `git ls-files -co --exclude-standard` lists, `git check-ignore` and Git's objects at `HEAD`, never an ignored file, and is silent where `.copier-answers.syntek-media.yml` is absent. It prints where media's guide starts (`how-to/src/TEMPLATE-GUIDE/syntek-media/01-overview.md`), media's update procedure (`how-to/workflows/syntek-media/04-update-the-template/`), that the guide is read-only and where a departure from it is recorded (rules 01 Section 10); where `.copier-answers.syntek-author.yml` stands, syntek-author's guide where its first chapter exists, or else that syntek-author must be v0.6.0 or later, updated now and before media from then on; `how-to` as a link, a root entry that differs from it only in letter case, and a guide Git ignores; the owner's files at the guide's paths (a shared file `HEAD` holds, or an untracked one, whose bytes differ from the template's, and a file of media's own `syntek-media/` folders that `HEAD` holds and the work tree no longer matches), each tracked one with `git show HEAD:<path>`, an untracked one marked as not in Git, which the update report then puts back, unless another template wrote it or Git does not hold it, with the `SYNTEK_UPDATE_REPORT=off` branch and, below Python 3.14, the line that `family-update.py` will not run; every file under `how-to/` that Git does not ignore and no template ships, a folder named for any template whose answers file stands at the root counting as that template's; and, where `opencode.json` exists, the permissions script's `--check` and then `--write`. Each list stops at 40. It ends with media's re-run command. `--help` prints its header.
- `family-update.py` — **every brand kind, every update and every copy; D11's third exception.** syntek-author's family-shared script (syntek-author D48, D51, D52), vendored byte for byte from its `v0.9.1` tag, mode 755, repository scope, and never edited here (D81). The family 'update' block runs it last in `_migrations`, unversioned, and the `baseline` task last in `_tasks`, both through `_copier_python`. On Python 3.14 an update ends with media's own report ('▸ syntek-media update report'), a render record under `refs/syntek-media/` inside `.git`, the refresh of the listed family files the owner never changed, the offers of the listed settings entries and MCP servers, once each, and the restore of `how-to/`; `baseline` records the copy's render and makes the same offers to the files a copy kept. `SYNTEK_UPDATE_REPORT=off` reports conflicts and deletions only and restores nothing, until the next full update; `--pretend` runs no migration. Below Python 3.14 it does nothing and prints a framed message that `family-update did NOT run`. It always exits `0`.
- `family-refresh.json` — **media's own data, not family-shared**, in syntek-author D48's format 1, `"template": "syntek-media"`: `refresh` lists the twenty-seven family files (the thirteen working-practice files and D84's fourteen), `restore` names `how-to`, the settings lane lists the two compaction values and the output style, the seed's handoff-hook and guide-guard entries, its denies and its asks (never the six allows, and never the data-root guard, which reaches new copies only), and the mcp lane names the two family servers and the five MCP files' key paths. An entry is offered only where the new render's `settings.json` holds it too. No manifest lists it; `coexist-test.sh` check 22 holds its family lists to the tag's, and `shipped-seeds.sh` check 31 its shape. A one-way door: an entry 0.6.0 lists reaches every project and cannot be withdrawn.
- **How each runs.** One `_migrations` entry per script in `copier.yml`, keyed by `version:` and run at `_stage == 'after'`, from the project root, with two stated exceptions, both unversioned and vendored: `agents-outside-link.py`, whose two entries run first, at both stages of every update, and the family 'update' entry, which runs `family-update.py` last. `v0.4.2` keeps its `python3` entry; `v0.6.0` runs through `_copier_python`, the interpreter running Copier. Copier runs a versioned entry only when the update crosses its version, read from the template's git tags; an update to an untagged `HEAD` still numbered below it does not, and no migration ever runs on `copier copy`.
- **By hand.** The update's clone of the template is deleted when the update ends, so each versioned script ends by printing the command that clones the release from the source in the answers file and runs it again (`v0.6.0-how-to.py` with `python3`, from the project root); `family-update.py` prints its own report and runs again with every update; `agents-outside-link.py` needs no clone, and prints its hand fix instead, which the README and the bridge give in these words: If an update stops before it ends (a refused answer, Ctrl-C at a question, or Copier failing as it cleans up after the render), the link stays held as `.agents.syntek-held`, and the next update refuses the changed tree; where the link is committed and the update stopped after its render, Copier has already put an identical `.agents` link back. Put the link back from the project root, in a POSIX shell (Terminal on macOS and Linux, Git Bash on Windows; never PowerShell's `rm`), before anything else, and before discarding the stopped update with `git reset --hard` and `git clean -fd`, which would delete a held link Git does not track. First check what stands at `.agents`: `ls -ld .agents .agents.syntek-held`. Where it shows no `.agents.syntek-held`, nothing is held: stop here and change nothing. Where `.agents` is a link (its line shows `->`), remove that link alone with `rm .agents` (never `rm -r`, never a trailing slash); where it is a folder or a file, move it aside to a name nothing holds yet (`ls -ld .agents.from-update` finds nothing) with `mv .agents .agents.from-update` (no trailing slash), which holds what the update wrote (check it, and delete nothing in it that is yours). Then, once `ls -ld .agents` finds nothing, run `mv .agents.syntek-held .agents` (no trailing slash). Never run that `mv` while `.agents` stands: it would put the held link inside it, and inside the folder outside the project where `.agents` is a link. Then update again; where `git status` still shows changes (a stop after the render), discard the stopped update first: run `git clean -n -d`, a dry run, move out of the project anything of yours it lists, then `git reset --hard && git clean -fd`. Where the held link was committed beside an identical `.agents` link, the next update moves nothing, says so, and asks you to remove the held link (`rm .agents.syntek-held`), commit, and update again.
